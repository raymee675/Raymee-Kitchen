# 提供ボックス2方式の試用実装計画

作成日：2026年10月18日　｜　状態：実装・型確認・Pages/PCビルド・隔離データと実画面での確認完了。未公開。

## 目的と期待する動作

現在の「呼出あり」方式を保存し、回収済み完成品を自動で全件表示する「自動一覧」方式を追加する。利用者は2方式を選んで試用できる。調理・記録・保存の共通処理は共有し、画面と提供期限の扱いだけを明示的な方式設定で切り替える。

| 動作 | 呼出あり（既定） | 自動一覧（追加） |
| --- | --- | --- |
| 表示 | 現行のID選択・中央ボタンによる検索、最大5検索を維持 | 回収と同時に全完成品を一覧表示。呼出UIなし、表示件数で切り捨てない |
| 30分期限 | 未検索なら期限で提供済み。検索済みなら期限切れで提供不可 | 未検索自動提供は行わず、期限切れも提供不可として一覧に残す |
| 一覧から外す | 現行の×は表示だけ解除。提供操作は別 | 各行の「管理終了」で、その個体の管理とタイマーを終了 |
| 管理終了結果 | 現行動作を維持 | 期限前は提供済み、期限以降は提供不可として記録を保持 |

「表示数の上限なし」は自動一覧で表示対象をslice等で制限しない意味とする。現在の192 IDの全体上限や採番規約は変更しない。呼出ありの最大5検索は保全する。来客数など別の集計機能は追加しない。

## 調査結果・制約・ブランチ

- 未検索自動提供を含む現在版は `ver-1.0` の `641b47c` に保存済み。追加実装は `codex/no-recall-completion` で行う。公開中の `main` は `32aca2a` のままとし、push・公開は行わない。
- `app/kitchen.tsx` は検索結果だけを表示し、検索ID配列を5件に切っている。`completionItems` 自体に表示件数の切り捨てはない。追加方式はこの配列を直接描画する。
- `CompletionItem` の `isRecalled` は現行の検索履歴であり、追加方式の自動表示を検索と見なしてtrueに変更しない。`settleUnsearchedCompletions` を追加方式では全経路で呼ばない。
- `remove` の完成品処理は既に、記録を期限前なら `servedAt=now`、期限以降なら `unavailableAt=deadline` に確定し、完成品配列から除外する。個別管理終了に再利用できる。終了後の記録はCSV対象として残り、タイマーの稼働対象から外れる。
- 完成品除外後は画面IDが詰め直される。現在のremoveはIDとversion中心のため、続けて押した別行のコマンドが再採番後の別個体へ当たるリスクがある。追加方式の終了コマンドはentityKeyとgenerationを照合する。
- 保存キー `...:single-phone-board:v1` と編集ロックは現在1種類。JSONバックアップv1には方式識別がない。方式ごとの独立保存と、復元時の方式照合が必要である。

## 設計・実装手順

1. **方式設定と選択**：`CompletionVariant = "recall" | "all"` を共通の小さな設定モジュールに定義する。Pages起動時にURLの `?completion=all` を追加方式、それ以外を既定のrecallと解決し、その起動中は固定する。既存のデータ管理ダイアログに「呼出あり」「自動一覧」の2択を置き、選択中の方式と「データは方式別に保存」を示す。198pxの既存操作領域へさらに常設ボタンを増やさない。切替は同じページのqueryを変更して全再読込する。pending・復元・切替処理中は選択不可とし、正常な画面では現在の保存キューが終了してから遷移する。読込障害で停止していても、処理待ちがなければ別方式へ切り替えられる。方式選択のたびに既存盤面をコピー・消去・変換しない。
2. **保存の分離**：`local-kitchen-storage.ts` の保存関数群にキー／方式の設定を渡せるようにし、引数省略のrecallでは既存キーを一字も変えない。allは例として `...:single-phone-board:v1:completion-all` の独立キーを使用する。`useKitchenLocal(variant)` の編集ロック、読込・保存・storageイベント、復元元raw照合、保護停止からの復旧、旧生地リセットまで、全経路を選択中キーへ統一する。双方の方式は同時に別タブで開けるが、同じ方式の複数編集は従来どおり排他にする。初回のallは空盤面から始める。
3. **バックアップの識別**：recallは既存のバックアップv1を維持し、旧v1はrecall専用と解釈する。allのバックアップは同じformat名の `formatVersion:2` と `completionVariant:"all"` を持つ。parserには現在方式を渡し、違う方式のバックアップ、識別が欠落／不正なv2を復元前に拒否する。既存の旧アプリもv2を拒否するため、allデータを旧recallへ誤復元できない。バックアップ名にall等の識別を付ける。現在の盤面schema13と記録形式は共用し、方式分離だけを理由とした盤面schema変更は行わない。
4. **期限処理の分離**：`useKitchenLocal` の精算呼出しを一つの方式ポリシーへ集約する。recallは現行の起動、sync、操作直前、100ms tickの期限検出、復帰、復元、prepareSnapshot、prepareExportSnapshotの精算をすべて維持する。allはそれらすべてで未検索自動提供を無効化し、時刻更新と `completionStatus` による「提供不可」表示だけを行う。記録やisRecalledを偽装して精算を抑制しない。
5. **自動一覧**：allは呼出UIと検索結果を描画せず、`completionItems` 全件を作成順で表示する。各行は安定した記録ID、提供可否、残り時間（期限切れは0）、独立した「管理終了」ボタンを持つ。空の場合は短い空表示を置く。固定／最大高さの内部縦スクロール、タッチのスワイプ、マウスホイール、キーボード操作を使え、最後の行まで到達できる。件数の切り捨てやページ全体を覆う重なりは設けない。スタイルはall用クラスへ局所化し、recallの行や既存鉄板操作を変えない。
6. **個別終了の安全性**：既存のremoveへ任意の `expectedEntityKey` を追加してparseで検証・保持する。値があるremoveは完成品／鉄板上の品への適用前にそのkeyを照合し、不一致は既存の競合として拒否する。guard付きの完成品removeでは、generationの安全整数上限を変更前に検査し、終了と同時にgenerationを1増やす。完成品除外は鉄板上のIDも詰め直すため、keyを持たない待機中のstart／adjust／moveも古いgenerationとして拒否する必要がある。旧コマンドは引き続き受け付け、guardのないrecall側の手動removeは現行の世代動作を保つ。allの管理終了はクリック行のentityKeyから最新完成品を解決し、画面ID・version・generation・expectedEntityKeyを送る。処理中の同個体の重複押下を抑制し、失敗時は行を消さず既存通知を使用する。任意の確認ダイアログ、全件終了、Undo可能化は追加しない。二行を素早く終了した際も別個体に化けず、競合なら更新後に再操作できる。
7. **説明と共有経路**：ヘルプとREADMEの説明を方式に合わせる。WebMCPは既存の登録対象条件（Pagesでは登録しない）を維持し、すでに対応している経路の説明だけを必要に応じて更新する。今回の追加方式を理由としてPagesに新しい読取・変更ツールを登録しない。既存PC経路はrecallとして型・ビルド互換を保ち、新たなPCサーバー方式切替は追加しない。

## 影響ファイルと所有権

- **実装worker（1名）**：新しい `cooking-app/lib/completion-variant.ts`、`lib/local-kitchen-storage.ts`、`lib/use-kitchen-local.ts`、`lib/kitchen-model.ts`、`app/kitchen.tsx`、`app/globals.css`、`cooking-app/README.md`。必要なら `pages-client/src/main.tsx` の起動時設定も担当する。UIとhookの受渡しはパラメータ化または方式ごとの再マウントで行い、同じマウント内で条件によってhook順序を変えない。全面的なコンポーネント複製や記録モデル複製はしない。
- **primary**：ブランチ確認、統合、必要な検証、結果報告。独立コードレビューは実施しない。
- **planner**：本計画と、保存境界・終了結果の仕様変更が必要になった場合の改訂。

## 検証・受入条件

テストファイルの追加・テストスイート実行は行わない。型確認、Pages／PCビルド、差分形式確認と、隔離したデータを使う手動確認を実施し、未実施の実画面確認は成功扱いにしない。

1. queryなしでrecallが開き、既存キーの盤面と、検索・最大5件・×・提供・未検索期限精算が現行と同じ動作をする。
2. データ管理の選択でallへ移ると空の別盤面になる。両方式に別の調理状態を作り、切替・再読込・各方式のリセットを繰り返しても他方の盤面・記録・タイマー・復旧元rawへ影響しない。同方式の排他と別方式の同時利用が機能する。
3. allでは回収した品が即表示され、6件以上でも全件に到達できる。表示のためのrecall保存は不要。縦横・狭い画面で一覧をスクロールしても、鉄板や他操作を覆わない。
4. allの未検索品は30分を超えても自動提供されず、提供不可で残る。終了・再起動、復帰、CSV／JSON出力、JSON復元のいずれでも自動精算されない。
5. 期限前の管理終了でservedAtが処理時刻になり、期限以降の管理終了で不可時刻が元の期限になる。どちらも完成品一覧からだけ除かれ、安定記録IDと調理区間・回収時刻を保持する。個別管理終了後は同個体の稼働タイマーが残らない。
6. 再採番を伴う連続管理終了や保留中の鉄板操作が、別のentityKeyへ適用されない。guard付き完成品終了だけでgenerationが1増え、安全整数上限では変更前に停止する。保存失敗・競合時に行を先に消さず、保存成功後に表示を更新する。
7. recall v1とall v2のバックアップはそれぞれ自方式で往復でき、クロス復元はエラーとなり、どちらの盤面も書き換えない。復元プレビューでも方式を明示する。CSVの既存10列と終了結果を保持する。
8. `ver-1.0` の保存コミットを維持し、追加差分は `codex/no-recall-completion` にある。main・リモート・公開ページは変更しない。WebMCPの既存登録条件を維持し、Pagesに新しい登録経路を追加しない。

## リスク・未決事項・自己確認

試用の2方式は別データであり、切替は進行中の個体を移す機能ではない。方式を閉じている間も絶対期限は進むため、戻った際にはその方式の期限ルールを適用する。allでも既存192 ID上限は残る。これらは説明に短く明記する。

実装を止める未決事項はない。方式の初期値、選択方法、保存・編集ロック・バックアップの境界、期限処理の全入口、表示上限の意味、終了記録と誤対象防止を定義した。新しい依存や運用移行は不要で、既存コアを共有した局所変更で実現できる。

## 実施記録

- `ver-1.0` の `641b47c` を保存し、`codex/no-recall-completion` で実装した。公開用mainへの反映・push・デプロイは行っていない。
- 隔離したメモリー保存領域で、8完成品の保持、allで未検索精算しないこと、recallの精算維持、期限前／期限後の管理終了、記録保持、対象entityKey・古いgeneration・世代上限の拒否、旧removeの世代動作維持を確認した。方式別キーで他方の保存が変わらず、v1/v2バックアップの相互復元拒否も確認した。
- 隔離したローカル画面で8件の復元・全件表示・内部スクロール末尾到達を確認し、実際に焼き上がりを回収すると9件目が検索なしで追加された。Tab操作でも9件目の管理終了へ到達できた。
- 期限前と期限後の管理終了で該当行が消え、再読み込みしても戻らないことを確認した。回収した9件目の管理終了後、実際のJSON書き出しはall/v2・記録9件・保管8件であり、終了対象のservedAtを保持して保管配列から除外した。実際のCSVは10列・9行で最後の記録が提供済みだった。
- データ管理からrecallへ切り替えると独立した空盤面とm/n呼出UIが表示され、allへ戻ると保持した一覧が復元された。別方式バックアップは画面でも拒否された。別方式の2タブを同時に開けることも確認した。
- 横568×320では一覧の内部スクロールと鉄板領域が分かれ、ページの横・縦寸法が568×320以内だった。縦375×667でも横にはみ出さず、一覧内部とページの縦スクロールを使用できた。ブラウザーのerrorログは0件だった。
- 最終コードで型確認・Pages/PCビルド・差分形式確認が成功した。テストファイル追加・テストスイート実行は行っていない。PagesへのWebMCP登録は元の無効条件を維持した。
