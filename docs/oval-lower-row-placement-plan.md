# 下段限定の新規配置 実装計画

## 目的と期待動作

新しく配置するお好み焼きは、いずれの鉄板でも下段の空きマスに限って配置できるようにする。上段は下段からの移動先専用とし、上段の空きマスを画面からタップしても create 操作を送らない。上段に新規配置しようとした場合は、下段に配置するか既存のお好み焼きを移動するよう案内する。

画面の抑止だけに依存せず、共通の `applySnapshotCommand` の create 経路でも、正規化後の配置先セルが上段なら拒否する。これによりPC API、Pagesのローカル保存、画面内WebMCP操作のいずれから来ても同じ規則を適用する。

## 現行実装の根拠と制約

- `cooking-app/lib/kitchen-model.ts` は `GRID_CELLS` を行優先で定義し、`nearestGridCell(x, y)` で座標をセルへ丸める。現在の `applySnapshotCommand` の create 分岐は容量・占有を検査してIDを採番するが、セルの行を検査していない。
- PCの `server/storage.mjs` と Pagesの `cooking-app/lib/use-kitchen-local.ts` は共通の `applySnapshotCommand` を通す。PC APIは `parseCommand` 後に共通モデルを呼ぶため、モデルでの拒否が両保存経路に適用される。
- `cooking-app/app/kitchen.tsx` の `up` は楕円以外のタップを空きセルへの create に変換し、上段・下段を区別していない。`gridCellAt` でタップ位置をセルへ解決し、create時にはそのセル中心をコマンドへ渡す。
- 同ファイルのWebMCP `operate_kitchen` 説明には create 操作が記載されているが、配置可能な行の制約は記載されていない。板全体の `aria-label`、ヘルプ、空き板の案内も現在は空きマス一般への配置と説明している。
- `cooking-app/README.md` も空きマス一般から配置できる説明になっている。直前の変更により「下段から上段へのみ移動できる」規則は既に記載されている。
- 保存データの正規化はレガシー座標と過密データを保持する。今回の変更では既存の上段位置を移動・削除・再配置せず、読み込み、既存項目の操作、既存Undo履歴の処理を変えない。create時の既存の採番・Undo契約、温度・タイマー動作も維持する。
- リポジトリは `main` が `origin/main` と同期しており、調査時点で未コミット差分はない。

## 対象ファイルと担当範囲

1. **共通モデル担当 (Luna worker):** `cooking-app/lib/kitchen-model.ts`
   - create の座標を既存どおり `nearestGridCell` でセルへ正規化し、行が `GRID_ROWS - 1`（現行の下段）であることを容量確認やID採番より前に検証する。
   - 上段なら明確な制約エラーを返し、盤面、IDカウンター、Undo履歴を変更しない。
   - 新たな移行・保存データ正規化・Undo形式変更は加えない。

2. **操作UIと説明担当 (別のLuna worker):** `cooking-app/app/kitchen.tsx`, `cooking-app/README.md`
   - UIで空きセルのタップ先をセル化してから判定し、上段ならcreateを送らず、上段は移動専用である旨を案内する。下段なら既存の容量・占有検査後にcreateを送る。
   - ヘルプ、板のARIAラベル、空盤面の案内、WebMCP `operate_kitchen` 説明、およびREADMEで「新規配置は下段」「上段は下段からの移動先専用」を同じ意味で記す。
   - PCとPagesで共通画面を使うことを踏まえ、画面制御をモード分岐で分けない。

作業中の共有コードベースには既存差分がある可能性がある。実装担当は他者の編集を戻さず、最新ファイルの差分を確認して追従する。モデル担当とUI担当はそれぞれ割当ファイルのみを編集し、重複編集を避ける。Solが進捗を調整し、統合後に最終diffを確認する。

## 実装段階

1. 共通モデルのcreate経路に下段セル判定を入れ、拒否メッセージを明確にする。
2. 画面の空きセル操作を下段だけcreateに結び、上段タップでは案内を表示する。既存の下段→同列上段への移動操作には触れない。
3. 画面内のWebMCP説明、ARIA文言、ヘルプ、READMEの操作説明を同じルールへ合わせる。
4. 最終diffを確認し、型チェックとPC/Pagesのビルド、`git diff --check` を実行する。テストは追加・実行しない。

## 受け入れ条件

- 鉄板1・2の下段3セルは、空きかつ容量条件を満たせば従来どおり新規配置できる。
- 上段3セルへの空タップはcreateを送らず、上段が移動専用だと利用者に伝わる。
- 上段座標を指定するcreateコマンドは `applySnapshotCommand` が拒否し、項目・次ID・Undo履歴を変えない。したがってPC API、Pages保存、WebMCP経由でも上段createが成立しない。
- 下段配置済みの楕円は、従来どおり同じ鉄板・同じ列の空いた真上へ移動できる。上段項目、横移動、鉄板間移動は引き続きできない。
- 既存の上段配置、過密旧データ、Undo履歴は読み込み後も保持され、自動移行・削除・再配置されない。
- ID採番/Undo、温度、90秒タイマー、完成ボックスの振る舞いに変更がない。
- README、ヘルプ、ARIA、WebMCPが新しい配置規則と一致する。
- 指定の型チェック、PC/Pagesビルド、diff checkが成功し、テストは実行していない。

## 検証

`cooking-app` で `npm run typecheck`、`npm run build:pc`、`npm run build:pages` を実行し、リポジトリルートで `git diff --check` を実行する。テストケースの追加・テストコマンド実行はしない（上位のユーザー指示）。レビューでは、セル境界でnearest-cellが下段に解決される時の期待動作、拒否時に採番・履歴が進まないこと、UIが上段からcreateを送らないこと、共有モデル経由で全経路に規則が及ぶこと、旧盤面とUndoの保持、全説明文言の整合を確認する。

## リスクと未解決点

- createコマンドの`x`,`y`は任意位置だが、モデルは既存仕様どおり最近傍セルへ丸める。今回の判定も丸めた後のセル行に対して行い、座標の数値上の上下だけで拒否しない。
- 旧バージョンからの古いクライアントが上段createを送った場合も共通モデルで拒否される。UI側の案内は新しいクライアントを対象にする。
- 保存済みの上段楕円は新規配置規則の対象外であり、既存データを自動で下段へ移すことはしない。これはID、調理位置、Undoの破壊的変更を避けるための意図した制約である。
- createの入力座標が行境界付近の場合は、現行のnearest-cell判定結果に従う。UIはセル中央の座標でcreateするため、通常操作はこの境界の曖昧さを持たない。
