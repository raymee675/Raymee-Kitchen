# お好み焼き完成ボックス 計画

作成日：2026年10月4日　｜　状態：実装前

## 目的・期待動作

90秒の焼き上がりと、その後の完成ボックス保管を別の状態・タイマーとして扱う。盤面から完成ボックスへ移す時刻を従来の「回収時刻」とし、実行記録CSVに提供結果を追記する。

- 鉄板上の調理タイマーは従来どおり開始から90秒で赤くなる。赤くなった時刻は `startedAt + 90秒` であり、赤をタップして完成ボックスへ移した時刻とは区別する。
- 赤い楕円をタップすると鉄板から完成ボックスへ移し、そのコマンドを保存した時刻を `collectedAt` および30分タイマーの開始時刻にする。期限は開始時刻+30分。赤くなってからタップするまでの待ち時間は従来の温度別加熱時間と回収時刻に含める。
- 完成ボックスのアイテムを期限前にタップすると提供済みとし、タップ時刻を保存して30分タイマーを停止、アイテムをボックス表示から除く。
- 期限到達後は青色の「提供不可」として表示する。期限後のタップは提供済みにせず、ボックス表示だけを除く。再読み込み・復帰時にも絶対時刻から青色状態を再計算する。
- 30分タイマーは保存したepochミリ秒の開始時刻と期限から計算する。期限は正確な失効時刻として保存し、実行時に常駐するバックグラウンドタイマーには依存しない。提供前にタップされた場合は提供時刻が停止時刻、期限切れの場合は期限時刻が停止/失効時刻となる。
- 既存の盤外ドラッグ削除を維持する。待機中・90秒計測中の盤外削除は記録しない。焼き上がり後に盤外削除された楕円は既存方針どおり調理記録を残し、完成ボックスを経由しない即時「提供不可（盤外破棄）」とする。30分開始・期限時刻は空欄。
- Excel CSVはExecutionRecord／お好み焼きIDごとに1データ行を出す。温度列「温度区間(℃・開始順)」と秒数列「区間加熱秒数(開始順)」には、各区間の値を開始時刻順に ` | ` 区切りで並べ、同じ位置の温度と秒数を対応させる。温度不明も対応する秒数と同じ位置に残し、単一区間もリスト形式とする。合計秒数、および焼き上がり時刻、30分タイマー開始時刻、提供時刻、30分タイマー期限時刻、30分タイマー停止時刻、最終ステータス、提供不可理由は記録ごとに1回だけ出力する。
- 最終ステータスは提供済み／提供不可。完成ボックスで期限を待っている記録を途中で出力した場合は、確定前であることを隠さず「保管中」とする。既存の完了記録は提供経過を持たないため「導入前・判定不可」とする。

### CSV仕様の改訂履歴

- **旧仕様（廃止）**：この計画の初版では旧ヘッダー6列を同じ名前・順序で維持し、温度区間ごとに1行、IDとサービス情報を区間ごとに繰り返すとしていた。このCSV仕様は[実行記録の書き出し計画](execution-record-export-plan.md)で改訂され、現在はExecutionRecordごとに1行とする。

## 現行コードの確認結果・制約

- `cooking-app/lib/kitchen-model.ts`では `timer(item, now)` が90秒経過後に `done` を返す。現行 `applySnapshotCommand` の `remove` は赤状態で `collectRecord` を作って `items` から消し、`delete` は状態を問わず楕円を消す。加熱温度区間と完了記録は現在の未コミット実装にある。
- `cooking-app/app/kitchen.tsx` はPC版・Pages版共通の調理画面。赤い楕円タップが `remove` を送り、長押し盤外削除が `delete` を送る。画面内には既存のCSVダウンロードボタンとWebMCP `operate_kitchen` 説明がある。完成ボックス用の領域はまだない。
- PC版は `server/storage.mjs` が `boards.state` JSON `{items, records}` をSQLiteトランザクション内で更新する。Pages版は `local-kitchen-storage.ts` の同一localStorageキー（suffix `v1`、envelope schemaVersion 2）に `{items, records}` を保存し、共通モデルを呼ぶ。
- `use-kitchen.ts` はサーバー補正時刻で約100msごとに表示を更新、`use-kitchen-local.ts` は端末時刻で同様に更新する。復帰時は再同期/再読込されるため、30分表示は絶対期限から導出できる。
- `server/restore.mjs` は現在のSQLite board JSONと温度区間・実行記録を検証するため、新しい `completionItems` と拡張記録の検証・移行も対象にする必要がある。
- `docs/execution-record-export-plan.md` および実装関連ファイルには未コミット差分がある。そこを作り直さず、現行のCSV列と加熱区間記録に積み上げる。

## 保存モデル・移行方針

- Snapshot/盤面JSONに `completionItems` 配列を追加し、鉄板上の `items` と完成ボックス内の表示アイテムを区別する。ボックスアイテムはIDとversionを持ち、期限と調理情報は同じIDの実行記録から取得する。楕円UUIDは作成時の既存IDを使い続ける。
- `ExecutionRecord` の既存項目は保つ。次の項目を追加する：`cookCompletedAt`（開始+90秒）、`serveTimerStartedAt`（赤タップ・ボックス格納時刻）、`serveDeadlineAt`（+30分）、`servedAt`、`unavailableAt`、`unavailableReason`。記録は開始後の温度区間とサービス結果を保持する。提供前なら `servedAt` はnull、期限切れなら期限を `unavailableAt` とする。
- 赤楕円の `remove` はボックス移動と記録生成を一つのモデル遷移にする。完成ボックスでの `remove` は保存時刻を期限と比較し、期限前なら提供済み記録にして表示から除き、期限時刻以降なら提供不可として表示から除く。古い画面の遅延操作を提供済み扱いしないよう、PC側のコマンド処理時刻を基準に判定する。Pages版はlocalStorageの直列化キュー内の `Date.now()` で判定する。
- `delete` は鉄板上の楕円に限る。赤状態での盤外deleteは既存の回収記録を作りつつ即時の提供不可/盤外破棄とし、ボックス待ち・期限切れアイテムの削除経路にはしない。
- 完成ボックス、履歴、調理盤面はPCでは同じSQLite `boards.state` JSONに、Pagesでは同じlocalStorage値に保存する。これにより赤タップ、ボックス移動、記録生成を一つのトランザクション/一回の保存にまとめる。
- PCの旧JSON配列と現行 `{items, records}` のどちらも読み、空の `completionItems` を追加する。古い実行記録は保存済みの加熱区間を保持し、サービス項目を「導入前・判定不可」として正規化する。CSVの列名と出力形式は[実行記録の書き出し計画](execution-record-export-plan.md)に従う。既存の赤楕円はまだ `items` に残っているので、新版でタップされた時から30分計測を始める。
- PagesのschemaVersionを2から3へ上げるがlocalStorageキーは変えない。version 1/2を読んで既存items・recordsを保持し、空のボックスと旧記録の判定不可状態を補って一度に移行する。

## 受け入れ条件・検証

- 90秒経過で鉄板上が赤くなり、その時点では従来どおり調理完了として扱う。赤タップ時だけ鉄板から完成ボックスへ移り、そこで初めて30分タイマーが始まる。焼き上がり時刻と格納/タイマー開始時刻がそれぞれ別項目として保持される。
- ボックス内では期限まで残り時間が減り、開始時刻+30分で青色・提供不可へ切り替わる。ページを再読込/復帰しても期限計算が維持される。動作中の分単位タイマーやバックグラウンド常駐を必要としない。
- 有効期限より前のボックスタップは提供済み、`servedAt`を保存し、タイマーを止めて表示を除く。期限時刻以上のタップは提供不可とし、古い表示に基づく遅延操作で提供済みへ戻らない。青いアイテムをタップすると表示だけが消え、履歴は残る。
- 待機/計測中盤外deleteは記録なし。赤状態盤外deleteは既存どおり調理記録が残り、30分ボックスを通さない「提供不可・盤外破棄」となる。
- PC SQLite再起動後・Pages再読込後も完成ボックス、期限、提供/不可の履歴とUUIDが維持される。PC側の複数端末操作ではrecord二重生成/取り違えがない。
- CSVはExecutionRecord／IDにつき1行を出す。温度と区間秒数は「温度区間(℃・開始順)」「区間加熱秒数(開始順)」の ` | ` 区切りリストとして開始順に対応させる。合計秒数とサービス時刻・最終ステータス・理由は記録ごとに1回出力する。期限前の項目は「保管中」、期限後は「提供不可」、提供されたものは「提供済み」、旧記録は「導入前・判定不可」となる。
- 横画面と縦画面で鉄板操作および完成ボックスの操作ができる。ボックス件数0件/少数/複数で、スクロールや配置のため鉄板の主要操作が隠れない。
- 実装後は `git diff --check`、型確認、PC/Pagesビルドと差分レビューを行う。ユーザー依頼がないためテストの追加・実行はしない。可能ならブラウザーで時刻境界（期限の直前/期限/直後）を確認する。

## リスク・未確定事項

- ブラウザーが非表示・停止中はカウント表示の更新や通知を保証できない。絶対期限は保持され、再表示/再読込時に青へ追いつくが、期限時の音・通知はこの依頼に含まれない。
- 現行データにすでに保存された実行記録は30分タイマーの開始/提供情報を持たない。過去の結果を推測せずCSVで「導入前・判定不可」と示す。
- 焼き上がり後に盤外へドラッグした楕円は既存仕様を継続し、30分保管を経ない盤外破棄を「提供不可」に分類する。用語上の「提供不可」を期限切れのみに限定したい場合は、別の廃棄ステータスが必要。
- 期限前ボックスアイテムを書き出した場合は最終結果がまだ確定していないため「保管中」と記す。出力を確定済みだけに限定する要望があれば、CSV対象範囲を別途決める。
- 既に開いている旧PCブラウザーは完成ボックスを描画できない。実装公開時は接続中の調理画面を再読み込みして新しいUIへ切り替える必要がある。
