# 実行記録CSVを1 ID 1行にする計画

作成日：2026年10月10日　｜　状態：実装済み（独立コードレビュー済み）

## 目的・期待動作

温度変更で加熱区間が複数に分かれた場合も、CSVは実行記録（お好み焼きID）ごとに1行だけ出力する。全区間の温度と加熱秒数をそれぞれ開始時刻順の並行リストとして同じ行に保持し、区間と値の対応関係を読み取れるようにする。合計加熱秒数は数値を1回だけ出力する。

- 温度列の見出しを「温度区間(℃・開始順)」、秒数列を「区間加熱秒数(開始順)」とし、両列の値は ` | ` 区切りでシリアライズする。例：`96 | 98 | 温度不明` と `31.25 | 20 | 38.75` は同じ順序の3区間を表す。
- 1つの温度区間もリスト形式で出す。温度不明は既存どおり「温度不明」とし、対応する区間秒数の位置を保つ。
- 各実行記録のID、開始・回収時刻、合計秒数、完成ボックス関連情報、最終ステータス、提供不可理由は1行に1回ずつ出す。
- UTF-8 BOM、CRLF、CSV引用符エスケープ、ファイル名、日時表現、対象記録の範囲は維持する。

## 実装前の確認結果・制約

- 実装前の `cooking-app/lib/execution-record-export.ts` は、`records.flatMap` の中で各記録の `segments.map` を使い、温度区間ごとに行を出していた。開始時刻、回収時刻、合計秒数、提供情報なども区間数だけ繰り返していた。
- 共通データモデル `ExecutionRecord` は1件ごとに連続した `segments` を保持する。`normalizeExecutionRecords` は区間の連続性とID重複を検証するので、保存済み記録を新たにグループ化する必要はない。配列順が開始順である。
- 区間温度は整数または `null`、区間時刻はミリ秒。既存の `seconds` は秒を小数第3位まで整形する。温度不明の既存表現と区間秒数の精度を保つ。
- 実装前は `cooking-app/app/kitchen.tsx` の説明に行の形がなく、READMEと `docs/execution-record-export-plan.md` も旧来の区間ごと1行を記載していた。
- ID列はExcelで連番IDを文字列として扱わせるため、既存の `excelTextId` を通す必要がある。

## 受け入れ条件・検証

- 出力データ行数が入力 `records.length` と一致し、各実行記録が必ず1行になる。
- 1区間・複数区間の記録で温度リストと秒数リストの件数および順番が一致し、温度不明区間も同じ位置に残る。
- 区間秒数は既存どおり各区間のミリ秒差分を秒に整形し、合計秒数は全区間の生ミリ秒差分の合計を数値で一度だけ出す。
- 各記録のサービス時刻・ステータス・理由が1行に一度だけ出る。期限超過などの既存判定、Excel向けID式、BOM、CRLF、引用符処理は維持される。
- ヘッダーと利用者向け説明から、両リストが開始順で対応することが分かる。
- ユーザーの指示に従い、新しいテストは追加せずテストスイートも実行しない。実装後は最終diffの確認と、利用可能な型確認・ビルド等の非テスト検証だけを報告する。

## リスク・未確定事項

- 現行CSVを複数行単位で集計・取り込みしている利用者がいれば、列名と各行の意味が変わるため取り込み側の調整が必要になる可能性がある。現在確認できる利用法はExcelでの閲覧であり、他の機械処理契約は見つかっていない。
- ` | ` 区切りは各フィールド内の見やすい表現であり、Excelから区間を別セルとして扱うには追加の分割操作が必要。今回の要望は1 ID 1行の出力なので、別行・別列への区間展開はしない。
- 各温度区間は空でなく、記録単位のIDも一意であることを既存モデルの検証に依存する。CSV関数で新しい修復・集約ロジックは導入しない。
