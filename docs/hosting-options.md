# アーカイブ：アカウント共有を不要にする運用方式の検討

**2026-10-10更新：これは2026年9月27日時点のSite版からの移行案に関する履歴資料です。現在の運用・サポート対象は固定スマートフォン1台で使う[GitHub Pages版の正本](single-phone-github-pages-architecture.md)です。本文は当時の検討を保持しており、現行手順やホスティング方針ではありません。**

検討日：2026年9月27日。これは移行案であり、現在の公開サイトやアプリの動作は変更していない。

## 結論

PCとスマホを同じネットワークにつなげられる場合は、PC上に画面・API・SQLiteデータベースをまとめて置く方式を第一候補とする。スマホはブラウザーでアクセスし、ChatGPTやGitHubの個人アカウントを共有しない。

スマホのモバイル回線からも使う場合、またはPCを常時起動できない場合は、管理者所有のCloudflare Workers / D1へ移し、アプリ独自の端末登録を設ける方式が候補になる。管理者のクラウドアカウントを利用者に渡す必要はない。

同じWi-Fiを使えるかは確認中。インターネット接続があることと、同じローカルネットワークに接続していることは別条件。

## GitHubで代用できる範囲

| 方式 | 画面の配信 | 複数スマホの共有操作 | 評価 |
| --- | --- | --- | --- |
| GitHub Pagesのみ | 可能 | 共有状態を保存・更新する別の仕組みが必要 | 今回の要件を単独では満たさない |
| GitHub Actionsを常駐サーバーにする | 適さない | 安定した継続運転に不向き | 採用しない |
| Pages＋クラウドAPI・DB | 可能 | 可能 | 構成と認証の追加が必要 |
| PC上に画面・API・DBを置く | 可能 | 同じネットワークで可能 | 現場内利用なら推奨 |
| Workers / D1に画面・API・DBを置く | 可能 | インターネット経由で可能 | 別回線利用なら候補 |

[GitHub Pages公式説明](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)によると、PagesはHTML・CSS・JavaScriptを公開する静的ホスティング。現在のサーバー側認証・API・D1処理をそのまま移すことはできない。

[GitHub Actionsの制限](https://docs.github.com/en/actions/reference/limits)ではGitHub提供ランナーのジョブは最大6時間。自動テスト・ビルド・デプロイに使い、調理中のAPIを常駐させる用途には採用しない。自前ランナーをPCに置いても、PCサーバー自体の運用は別途必要になる。

ソース管理と更新の自動化にはGitHubを使える。[Cloudflareの公式手順](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/)にはActionsからWorkersへデプロイする方法がある。管理用の認証情報はCI側で保持し、スマホへ配布しない。

GitHubのリポジトリファイルをタイマーのデータベースとして頻繁に書き換える案は、今回の低遅延同期・競合制御・利用者の認証分離に適さないため採用しない。

## PCサーバー案

モバイル回線からも追加サービス料金なしでこのPCへ接続する方針の具体的な作業計画は [PC・モバイル回線向け実装計画](pc-mobile-implementation-plan.md) を参照。Cloudflare Oneのプライベート接続を使うため、各スマホに専用の接続アプリが必要。

構成：各スマホのブラウザー → 同じルーターのネットワーク → このPCのNode.jsサーバー → SQLiteファイル。

PCはルーターへの有線接続でもよい。スマホ同士やPCへの通信が禁止されたゲストWi-Fiは使えない。画面とAPIを同じPCから配信すれば、PagesとローカルAPIを組み合わせる必要はない。

実装変更：

1. Reactの調理画面・SVG・操作ルール・サーバー時刻を使う計算を再利用する。
2. ChatGPTログインを外す。専用の信頼できるLAN内だけならログインなしで利用できる。ただし、そのLANに接続した端末が操作できる範囲になる。端末を限定する場合は、PC側で承認する端末登録と失効可能な端末別セッションを設ける。
3. D1依存の保存処理をSQLiteへ置き換える。操作の二重適用防止と競合検出は、SQLiteのトランザクションを使って維持する。
4. 本番用にビルドした画面とAPIをNode.jsで配信する。開発用サーバーを運用サーバーに流用しない。
5. 起動用スクリプト、接続URLの表示、DBバックアップ手順、必要に応じてWindows起動時の自動起動を用意する。
6. スマホ実機で同時操作・通信断復帰・PC再起動後のデータ保持を確認する。

運用条件：

- 調理中はPCを起動し、スリープさせない。PC停止中は全端末の共有操作が止まる。
- 接続先が変わらないよう、ルーターでPCのアドレスを固定予約することが望ましい。
- Windowsファイアウォールは利用するプライベートネットワークの必要なポート・接続元に限定して設定する。ルーターのインターネット向けポート開放は不要。
- データはPCのディスクに保存する。端末側だけの保存にはしない。
- LAN内HTTPで運用する場合、現在使っている `crypto.randomUUID()` に代替処理が必要。[MDN](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/randomUUID)ではこのAPIはセキュアコンテキスト限定。サービスワーカー等も含め、通常のブラウザー利用とHTTPSでのPWA利用を区別して実装・検証する。

## クラウド案

料金、サービス比較、個別メール認証と端末登録、移行手順は [クラウド構成の詳細検討](cloud-architecture.md) を参照。

現在のWorkers / D1構成を活かし、Sites管理外の管理者所有環境へ移す。ChatGPTログインを端末登録方式などへ変更し、公開URLを知るだけで誰でも共有データを操作できる状態にはしない。

画面もAPIも同じWorkers側へ置けば、Pagesを別に設けるより構成をまとめられる。GitHubはソース管理とActionsによる更新に使う。管理者のCloudflare設定と、契約・使用量に応じた費用の確認が必要。料金の見積もりはこの検討の対象外。

PCを外部回線から利用する場合はVPNなどを別途構成する必要がある。PCの常時起動も引き続き必要になるため、最初の候補は「現場LANならPC」「回線を問わず使うならクラウド」とする。

## 2026年9月27日時点の実装で確認した箇所

- `cooking-app/app/page.tsx`：ChatGPTログインを要求する画面。
- `cooking-app/app/api/board/route.ts`：APIのChatGPT認証、入力検証、同一サイトからの操作確認。
- `cooking-app/db/kitchen.ts`：Cloudflare D1への依存、保存、版番号と操作IDによる制御。
- `cooking-app/app/kitchen.tsx`：再利用可能な調理画面、UUID生成、サービスワーカー登録。
- `cooking-app/lib/kitchen-model.ts` / `lib/use-kitchen.ts`：再利用可能な調理ルールと同期・時刻補正。

今回行ったのはコード確認と公式資料に基づく方式検討。PCへのスマホ接続、Windows常駐運転、移行後の動作はまだ検証していない。
