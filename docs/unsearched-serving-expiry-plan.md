# 未検索のお好み焼きを提供期限に提供済みとする実装計画

作成日：2026年10月17日　｜　状態：実装・型確認・ビルド・データ確認完了。実画面はブラウザー接続不可のため未確認。未公開。対象は現在運用している GitHub Pages / 端末保存経路。

## 目的と期待動作

回収から30分の提供タイマーの間、一度も検索されなかった完成品は、期限到達時に何ごともなく提供されたとみなす。実行記録の `servedAt` を元の `serveDeadlineAt` に確定し、完成品の保管配列から取り除く。後から検索しても「提供済み」と表示し、CSVと盤面バックアップにも確定した提供記録を残す。

期限前に検索された完成品は、従来どおり期限前は提供可能、期限到達後は提供不可とする。検索自体では提供確定もタイマー再開始も行わない。「×」による結果表示の解除、再読込、画面を閉じる操作で検索履歴を消さない。回収前の「未準備」検索は、その後に始まる30分タイマーの検索履歴には含めない。

## 確認した実装と制約

- `app/kitchen.tsx` の中央検索ボタンは現在 `deliverySearchIds` だけを変更し、検索した事実を保存していない。照合は完成記録の安定した `record.id`、鉄板上の `archiveId` による。`recall` が受け取る完成品の `id` は別の、詰め直される画面IDである。
- `lib/kitchen-model.ts` には既存の `CompletionItem.isRecalled` がある。新規回収は false、既存の `recall` コマンドは内部 `entityKey` と version を照合して true にする。これを30分計測中に検索された事実として再利用し、新しい検索フィールドやコマンドは設けない。
- 現在の `completionStatus` は期限だけで提供不可を導き、100 ms の画面更新は表示時刻だけを進める。表示上の判定変更だけでは、記録・バックアップ・CSVの提供済み確定にはならない。
- `normalizeExecutionRecords` は現在 `servedAt >= serveDeadlineAt` を拒否する。自動確定のため、等号を許可する必要がある。`normalizeCompletionItems` は提供確定済み記録を参照できないので、記録更新と完成品配列からの除外は同時に行う。
- 正規化は画面IDを詰め直す。自動確定による除外の後、古いIDと同じversionのコマンドが別個体に当たらないよう、自動確定が1件以上あるバッチでは generation を1増やす。revision も保存単位で1増やす。記録ID・entityKey・作成順は維持し、Undo内容は保全して既存正規化で参照IDを揃える。
- `readLocalBoard` の従来の移行保存は失敗を握りつぶす。今回の提供確定の保存失敗はその経路に混ぜず、既存の保存障害と同じく操作停止・状態表示へ伝える。
- 旧 schema 12 までの false は「検索されていない」と断定できない。schema 13 に上げ、旧形式の未確定完成品は `isRecalled:true` として移行する。過去の検索履歴が不明な品を自動提供済みにしないための判断であり、これらは従来の期限切れ扱いを保つ。既に確定した提供済み／提供不可記録は変更しない。

## 設計と実装手順

### 1. 純粋な期限精算と保存形式

`lib/kitchen-model.ts` に、正規化した盤面と現在時刻から期限到達した未検索完成品を精算する共通の純粋関数を置く。対象は `isRecalled === false`、同じ entityKey の記録に開始・期限が存在し、未確定で、`now >= deadline` のものだけとする。対象記録の `servedAt=deadline`、不可時刻・理由は null のままにし、対応完成品を除く。対象がなければ盤面とカウンターを変更しない。対象があれば generation の安全整数上限を検査して1増やし、既存正規化で整合させる。記録提供時刻の許容範囲は開始以上・期限以下にし、手動提供の `< deadline` 判定は維持する。

`lib/local-kitchen-storage.ts` は schema 13 と旧形式移行を実装する。schema 12 で導入された boolean 必須検査と schema 11 の厳密ID検査は閾値を維持する。schema 13 の false は保存された未検索状態として信頼できる。バックアップ parser は同じ移行を使用し、schema 13 のバックアップは検索状態・期限・確定結果を往復保持する。

### 2. 読込・時間更新・操作の保存

`lib/use-kitchen-local.ts` と端末保存経路に期限精算を接続する。起動、sync、画面復帰、操作直前、バックアップ復元完了時に、最新の保存データから現在時刻で精算する。画面を開いたままの場合も既存tickから期限到達を検出し、精算を既存 `mutationQueue` に1回だけ投入する。対象がない100 msごとの書込み・revision更新は行わない。

精算の永続化は編集ロックを持つ経路で、既存コマンドと復元に直列化し、最新値を再読込してから行う。自動精算の保存が成功してから snapshot を公開する。保存失敗を成功表示にせず、既存の保存障害処理で offline / status を示す。古い generation の待機コマンドは既存の競合として拒否し、再採番後の別品に適用しない。復元中やロックを持たない画面は勝手に精算を書き込まない。

get-only な読込や書き出し用 snapshot にも同じ純粋精算を使用できるようにするが、永続保存済みと一時的な出力用算定を混同しない。純粋な表示導出やCSVの文字置換だけで実装を完了しない。

### 3. 検索履歴の永続化

`app/kitchen.tsx` の検索を専用の非同期ハンドラーにする。検索された安定IDを `findDeliverySearchMatches` と同じ意味で entityKey に解決し、期限前・未確定で完成品配列にある一致対象だけに既存 `recall` を送る。送信時はその entityKey の最新完成品から画面ID・version・generationを取り、`expectedEntityKey` を必ず付ける。選択中の検索文字列をそのまま recall の画面IDとして送らない。

履歴保存が必要な対象は、保存成功後に結果一覧へ追加する。保存失敗時は検索済みを装わず既存通知で案内する。すでに検索済み、確定済み、未準備、該当なしの結果は保存操作を必要としない。期限以降の初検索は先に精算し、確定した提供済み結果を表示する。期限直前の検索と期限精算は保存キューの実行時刻で順序を決め、精算済みの品を遡って検索済みにしない。矢印によるID選択だけでは履歴を作らず、×は表示だけを解除する。

### 4. 書き出しと説明の整合

CSVとJSONの書き出しは、その操作時刻で精算した最新snapshotを利用し、直前のtickを待たず期限に到達した品も提供済みで出力する。可能な通常編集経路ではキュー経由で先に確定を保存する。`execution-record-export.ts` は記録自体の `servedAt` を既存どおり出力し、記録配列だけから検索状態を推測する独自のCSV判定は加えない。列数・列名は変更しない。

画面のヘルプおよび `cooking-app/README.md` の関連説明に、未検索の期限到達は提供済み、検索したものの期限到達は提供不可、旧保存データの検索履歴は復元できないため既存保管分は従来扱い、と簡潔に記載する。既存PC経路は型・共有正規化の互換を保つ。PCサーバーの新しい常駐精算や履歴移行は本計画の対象に広げない。

## 検証と受け入れ条件

テストファイルの追加とテストスイート実行は行わない。型確認、Pagesビルド、共有モデルのPCビルド、差分形式確認と、隔離した検証データでの手動確認を行う。実施した検証だけを報告する。

1. schema 13 で新規回収し未検索のまま、期限直前は保管中、期限ちょうどから提供済みになる。servedAt は処理時刻ではなく期限と一致し、完成品配列から除かれ、記録は残る。
2. 一度期限前に検索した品は、それだけでは提供済みにならない。×で閉じ、再読込しても履歴は true のままで、期限到達後は従来どおり提供不可。手動の期限前提供・期限後取り出しの意味は維持する。
3. 回収前の検索は回収後の未検索判定に影響しない。期限後の初検索は提供済みを返し、期限や記録を再開始しない。再採番で検索IDと画面IDが異なっても、検索したentityKeyだけが true になる。
4. 非表示・終了中に期限を過ぎ、後から起動／復帰しても期限で提供済みに確定する。自動確定後の再読込やJSON往復で結果を保持し、繰り返し精算でrevision/generationを増やさない。
5. 期限到達直後にCSV／JSONを書き出しても提供済み・提供時刻が正しい。新形式の期限前バックアップを期限後に復元すると、復元直後に未検索品が期限で提供済みになる。
6. schema 12以下の保管品は true として移行し、検索履歴不明の既存品を新たに自動提供済みへ変更しない。確定済み記録や旧不明記録の結果は不変。不正な現行形式で保存保護を弱めない。
7. 同時に複数の未検索品が期限到達した場合は1保存バッチで確定し、generationを1増やす。古いgenerationの待機操作は拒否され、IDが繰り上がった別品を変更しない。鉄板上の品・安定記録ID・時刻区間・生地タイマー・Undoの内容を壊さない。
8. 自動精算や検索履歴保存に失敗した場合は成功扱いしない。保存障害・復元排他・編集ロックの既存保護を維持する。ログを増やしたり確認ダイアログを追加したりしない。

## リスク・未決事項・自己確認

旧UIの検索履歴は保存されていないため復元不能である。schema 13 の保守的移行で既存データの意味を守り、切替後に回収した品から未検索自動提供を確実に適用する。自動精算で画面IDが変わる点はgeneration競合で保護する。時計は既存の端末時刻補正を使用し、新たな時間管理方式は導入しない。

実装を止める未決要件はない。データ状態と画面表示を分け、純粋な精算、永続保存、検索の順序、バックアップ互換、書き出し境界を定義した。公開・pushは今回の依頼には含めない。
