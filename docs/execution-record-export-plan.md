# 実行記録の書き出し 計画

作成日：2026年10月4日　｜　状態：実装済み（CSVの行単位を改訂）

## 目的・期待動作

調理画面から、回収済みのお好み焼きの実行記録をExcelで開けるCSVとして書き出す。楕円作成時にすでに付与しているUUID v4をお好み焼きIDとして維持し、書き出しにも同じIDを含める。

- 対象は90秒経過後に回収された楕円。通常の`remove`と、赤くなった後の盤外`delete`を回収記録にする。待機中・計測中の盤外`delete`は廃棄として記録しない。盤内移動は記録に影響させない。
- タイマー開始時刻は`start`を保存した時刻、回収時刻は赤状態で`remove`または`delete`が成立した時刻を使う。PC版ではSQLite更新時のサーバー時刻、Pages版ではlocalStorageへ保存する操作時の端末時刻を使う。
- 開始時の温度から加熱区間を開始する。計測中に温度が変わった場合はその時点で区間を閉じ、変更後の温度の区間を開始する。回収時に最後の区間を閉じる。待機中の温度変更は開始時の温度にだけ反映する。
- 温度ごとの秒数はタイマー開始から回収までを計測する。赤くなった後、実際に回収されるまでの時間も最後の温度区間に含める。
- CSVは実行記録（お好み焼きID）ごとに必ず1データ行を出す。温度は「温度区間(℃・開始順)」、秒数は「区間加熱秒数(開始順)」の列に ` | ` 区切りで並べ、同じ位置の値を対応させる。温度不明の区間も「温度不明」として秒数との位置関係を保つ。区間秒数はミリ秒を保持し小数秒で出し、1区間の場合もリスト形式にする。合計秒数は全区間の和を記録単位で一度だけ出す。
- UTF-8 BOM、CRLF、CSVの引用符エスケープを使い、Excelが日本語列名を文字化けさせず開けるようにする。日時はエクスポート端末のローカル時刻で `YYYY-MM-DD HH:mm:ss` 形式とする。ファイル名は日時付きCSVとする。
- エクスポートは完了記録をすべて含める。現在盤面にある待機・計測中・焼き上がりの楕円は含めない。履歴を消去するUIは今回追加しない。

## 現行ライフサイクルと制約

- `app/kitchen.tsx`で新規楕円に`createUuid()`を呼び、`id`としてUUID v4を割り当てている。既存のIDを維持し、別採番や画面表示用IDを追加しない。現状IDは盤面上では表示されないため、CSVをIDの閲覧・照合先とする。
- `lib/kitchen-model.ts`の`start`は`startedAt`を設定し、`adjust`は待機中・計測中の現在温度を更新する。`remove`は赤状態のみ許可して楕円を削除する。盤外移動に使う`delete`は状態を問わず削除する。
- PC版は共通モデルから`server/storage.mjs`の`executeCommand`へ進み、`BEGIN IMMEDIATE`内でSQLiteの`boards.state` JSONとrevisionを更新する。現在の`state`は楕円配列だけで、完了済み記録は保持していない。
- Pages版は同じモデルを`use-kitchen-local.ts`で呼び、`local-kitchen-storage.ts`のlocalStorageスナップショットを一括更新する。現在のlocalStorage envelopeはschemaVersion 1で、既存の楕円はUUID・温度・開始時刻を保持している。
- 両版は同一の`Snapshot`/`applyCommand`経路を使うため、完了記録をコマンドの原子的な状態変更と一緒に保存する。ブラウザー内CSV生成に追加依存は不要。

## 記録スキーマと移行方針

- 共通モデルに完了記録配列を追加する。1件は `{ id, startedAt, collectedAt, segments }`、区間は `{ temperature, startedAt, endedAt }` とし、時刻はUnix epochミリ秒。完了記録の区間は連続し、最初の区間がタイマー開始、最後の区間が回収で終わる。
- 計測中の楕円にも温度区間を保持する。最終回収操作では最後の区間を閉じ、その楕円を盤面から取り除き、完了記録へ移す。`remove`または`delete`と記録追加は同じコマンド適用・保存処理内で行う。
- 記録配列と進行中区間を盤面と同じ保存単位に入れる。PCのSQLite `boards.state` は旧配列を `{items, records}` 形式へ正規化して保存する。Pagesは既存localStorageキーを変えず、envelope schemaVersion 1を読んで `records: []` と初期区間情報を補ったschemaVersion 2へ移行する。新形式では以後もitems・recordsを同時に保存する。
- 旧データ中の開始済み楕円は温度変更履歴が存在しない。過去温度を推測して記録しない。移行前の開始から最初に追跡できる時点までを「温度不明」区間とし、その後の変更区間は通常どおり記録する。追跡区間が一度もないまま回収された場合は、開始から回収までを温度不明の1区間として出力する。開始前の楕円は、開始時点の温度から通常の記録を始める。

## 影響範囲・担当

- **GPT-6 Luna実装worker（単独でデータ契約全体を担当し、同じファイルの並行編集はしない）**：
  1. `cooking-app/lib/kitchen-model.ts`で温度区間・完了記録の型とスナップショットを定義し、start/adjust/remove/deleteの記録遷移を実装する。完了後の`delete`だけ回収記録へ含め、未完了deleteを記録しない。
  2. `cooking-app/server/storage.mjs`で旧SQLite JSON配列を保全しながら移行し、itemsとrecordsを1トランザクションで更新・返却する。
  3. `cooking-app/lib/local-kitchen-storage.ts`と`cooking-app/lib/use-kitchen-local.ts`で旧schemaVersion 1を保全移行し、Pages版でも同じ遷移を保存する。既存のlocalStorageキーを維持する。
  4. `cooking-app/lib/execution-record-export.ts`（新規）にCSV変換、日時/秒数整形、BOM・CRLF・引用符処理をまとめる。`cooking-app/app/kitchen.tsx`の共通画面へ書き出しボタンを追加し、PC版とPages版の両方で同じ記録をダウンロードできるようにする。
  5. `cooking-app/README.md`に記録対象、列、保存範囲、Pages版ではブラウザー保存領域に依存することを追記する。
- **Sol coordinator**：計画と実装差分を確認し、機能契約・移行互換性・CSVの意味を調整する。
- **実装者とは別のGPT-6 Luna reviewer**：完了記録が重複/欠落しないか、同時操作と旧データ移行を中心に独立レビューする。

## 受け入れ条件・検証

- 作成時のUUIDが運用中に変わらず、CSVはIDごとに1行を出す。複数温度区間は、開始順に対応する温度リストと秒数リストで保持する。
- 待機中に温度を複数回変更して開始した場合、開始温度のみが記録される。計測中に温度を複数回変更した場合、各区間の秒数が境界時刻と一致し、その合計が開始から回収までに一致する。
- 90秒より前のremoveは拒否される。赤状態でのremoveと盤外deleteは1件だけ完了記録を作る。待機・計測中の盤外deleteは履歴に残らない。移動と温度表示は従来どおり動く。
- PCで完了記録がSQLiteに残り、更新/再起動後に調理画面から全履歴をCSV出力できる。Pagesでは再読み込み後も記録が残り、CSVを出力できる。
- CSVはBOM付きUTF-8、CRLF、日本語ヘッダー、適切にエスケープされたフィールド、開始/回収のローカル日時、同じ順序で対応する温度・区間秒数リストを含み、Excelで開いて列分割・日本語・数値を確認できる。
- SQLiteの旧state配列とPages schemaVersion 1から、既存の盤面/開始時刻/温度/IDを失わず新形式に移行する。旧開始済み楕円の未知区間は、推定値ではなく「温度不明」として出す。
- 実装後は差分レビュー、`git diff --check`、型確認、PC/Pagesビルドを行う。テストの追加・実行はユーザー依頼がないため行わない。ブラウザーで既存保存状態の移行とダウンロードを確認できる環境では、PC/Pages双方で実動作を確認する。

## リスク・未確定事項

- Pages版は端末内localStorageに記録を保存するため、ブラウザーデータ削除・端末交換で履歴が失われる。CSVを定期保存する運用は可能だが、自動バックアップは今回含めない。
- 履歴は消去UIなしですべて保持する。レコード量が大きくなった場合のPages localStorage容量を観察し、必要になれば別要件としてエクスポート後の削除/アーカイブや保存上限を設計する。
- 今回より前に回収済みの楕円は盤面からすでに削除されており復元できない。旧状態で計測中の温度変更履歴も保存されていないため、その部分は不明として扱う。
- `delete`はドラッグで盤外へ出す操作とWebMCP等からの状態不問操作の両方に使われる。done時を回収として扱うことは本計画の仕様であり、未完了時は廃棄とする。

## 実装メモ

- `Pancake.segments`に温度区間を保持し、`Snapshot.records`へ回収完了時の区間を同じ保存単位で追加するよう実装した。PCの旧state配列とPagesのschemaVersion 1は、盤面を保ったまま新形式へ移行する。
- 初回実装では、共通画面にCSV書き出しボタンを追加し、温度区間ごとに1行出力していた。この区間ごと1行のルールは2026年10月10日の仕様改訂で廃止され、現行仕様では実行記録ごとに1行とする。
- `git diff --check`、Nodeの構文確認、TypeScript型確認、PC/Pagesビルドに成功。テストは実行していない。
- 独立レビューで `cooking-app/server/restore.mjs` が旧配列形式だけを許容し、更新後のSQLite形式を復元時に拒否する不整合が判明。復元時の検証を旧配列と `{items, records}` の両方へ対応させ、記録データを保全する。

## 仕様改訂（2026年10月10日）

- 旧仕様の「温度区間ごとに1行」は廃止した。CSVは各ExecutionRecord／お好み焼きIDにつき1行を出力し、区間の増減で行数やIDの重複が生じない。
- 「温度区間(℃・開始順)」と「区間加熱秒数(開始順)」に、各区間の値をそれぞれ開始時刻順で ` | ` 区切りして出す。各リストの同じ位置が対になり、温度不明もその区間秒数と同じ位置に残す。単一区間もリスト形式にする。
- 合計秒数、開始・回収・焼き上がり・保管・提供時刻、最終ステータス、提供不可理由は各記録につき1回だけ出力する。ID保護、CSV引用符、UTF-8 BOM、CRLF、日時とファイル名の形式は維持する。

## 計画改訂（バックアップ復元）

- **追加影響範囲**：GPT-6 Luna実装workerが `cooking-app/server/restore.mjs` の `assertDatabase` を更新する。盤面状態JSONが旧配列なら従来どおり受け入れ、新形式なら `items` 配列と `records` 配列を検証して受け入れる。復元コピー時にstateを書き換えないため、新形式の実行記録はそのまま保全される。
- **追加影響範囲**：同workerが `cooking-app/lib/kitchen-model.ts` で、create時に進行中itemsだけでなく完了recordsのIDも照合し、完了済みのお好み焼きIDを再利用した作成を拒否する。保存済みrecords内のID重複も正規化時に不正として拒否する。
- **追加受け入れ条件**：新形式のPCバックアップを復元でき、`items` と `records` が保持される。旧配列形式のバックアップも引き続き受け入れる。壊れた形式は復元前に拒否する。
- **追加受け入れ条件**：完了済みお好み焼きと同じIDのcreateを拒否し、CSV上で複数のお好み焼きが同じIDとしてまとまらない。
- **追加検証**：`node --check server/restore.mjs` と差分レビューを行う。テストはユーザー依頼がないため実行しない。
