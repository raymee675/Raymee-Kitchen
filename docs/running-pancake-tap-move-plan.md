# 調理中のお好み焼きのタップ移動 実装計画

## 目的と期待動作

タイマー開始後、調理中（`timer(item, now).state === "running"`）の下段のお好み焼きをタップすると、同じ鉄板・同じ列の真上にある空き上段マスへ自動で移動する。既存の下段限定配置と下段から同列上段への移動制約を守り、既存の `move` command を使う。

- 下段の待機中のお好み焼きのタップは従来どおり90秒タイマーを開始する。
- 下段の調理中のお好み焼きのタップは上段への移動を試みる。移動先が使用中、鉄板が過密、または移動が成立しない場合は楕円・タイマー状態を変えず、理由が分かる案内を表示する。
- 移動が成功してもタイマーは継続し、開始時刻、経過時間、温度、IDを維持する。
- 焼き上がり状態のタップは従来どおり完成ボックスへ移す。
- 上段の調理中楕円は上段から移動できない規則を維持する。タップは移動させず、必要なら上段は移動不可であることを案内する。温度矢印と長押しドラッグの既存動作を維持する。
- 楕円本体のEnter/Spaceは画面タップと同じ `perform(..., "tap")` を通すため、下段の調理中楕円では同じ移動になる。ARIAラベルも状態と操作に合わせる。
- 画面の使い方、WebMCP操作説明、READMEに、新しいタップ操作を記載する。

## 現行実装の根拠と制約

- `cooking-app/app/kitchen.tsx` の `perform(item, action)` は、`tap` で待機中なら `start`、焼き上がりなら `remove` を送信し、調理中は何もしない。タップとEnter/Spaceはこの関数を共有している。
- 同ファイルの `run` は操作結果を受けてmove成功の通知を出す。移動先の事前検査には既存の `gridMoveBlockReason` と、ドラッグ時に使う具体的な理由別メッセージを再利用できる。送信失敗時の表示経路も実装前に確認し、競合でサーバー側が拒否した場合に案内が消えないようにする。
- `cooking-app/lib/kitchen-model.ts` の `gridMoveBlockReason` は下段起点、同一鉄板、同列の直上、空きセル、過密状態を検査する。move適用は既存項目の `plate` と座標を変えてversionを進めるため、`startedAt`、温度、区間、IDを保持する。通常moveはタイマー状態で制限されていない。
- `applySnapshotCommand` は既存move制約を共有モデルで適用する。ページUIからの自動移動もこのコマンドを使うため、通常はモデル変更不要。UIの事前判定は利便性のためであり、共有モデルの検証を迂回しない。
- 下段から上段へ移す仕組みは、ドラッグ移動とモデル検証として既に実装済みである。今回の対象は下段の「調理中」タップに自動移動を割り当てる画面動作と、その案内文である。
- READMEは新規配置・開始・上向き長押し移動を別々に説明している。画面の使い方、鉄板のARIAラベル、WebMCPの `operate_kitchen` 説明も `kitchen.tsx` 内にある。

## 実装手順

1. `perform`、エラー表示、状態別ARIA、ドラッグ移動経路を再確認する。
2. 下段のrunning状態のtapだけを、真上セルへの既存 `move` command に結びつける。セル特定と可否判定は共通のグリッドヘルパーを使う。
3. 事前判定で不許可の場合は盤面を変更せず理由を通知する。許可後の送信は既存generation/version付きmove経路を使い、競合時はモデル拒否の内容もUIに表示する。
4. 待機中の開始、完了後の完成ボックス移動、上段移動禁止、温度矢印、ドラッグ、Undoを保つ。Enter/Spaceにも同じタップ意味を適用し、ARIA説明を更新する。
5. ヘルプ、WebMCP説明、READMEの関連文言を更新し、型チェック、PC版・Pages版ビルド、`git diff --check` を実施する。テストは追加・実行しない。

## 受け入れ条件

- 下段のblankをタップ、またはEnter/Spaceで操作すると従来どおり計測が始まる。
- 下段のrunningをタップ、またはEnter/Spaceで操作すると、同じ鉄板・同じ列の空き上段へ移動する。位置が変わってもタイマーが継続し、開始時刻・温度・IDを維持する。
- 上段が使用中、または既存の過密制約により移動できない場合、項目、タイマー、温度、Undo可能状態に意図しない変更がなく、利用者に理由が伝わる。
- 下段のdoneタップは完成ボックス移動のままである。上段のrunning項目はタップしても移動しない。
- 上段からの移動禁止、左右・同段・鉄板間移動禁止、下段のみの新規配置を保つ。
- 温度矢印、長押しドラッグ、Undo、ID・記録の既存契約を変えない。
- ARIA、ヘルプ、WebMCP、READMEが新しい操作と一致する。
- 型チェック、PC版/Pages版ビルド、diff checkが成功する。テストは追加・実行しない。

## 検証

`cooking-app` で `npm run typecheck`、`npm run build:pc`、`npm run build:pages` を実行し、リポジトリルートで `git diff --check` を実行する。テスト追加・テスト実行は行わない。レビューでは、状態境界（blank/running/done）、上段runningのtap抑止、occupied/over-capacity時の無変更と案内、version/generation競合時のエラー表示、タイマー継続、Enter/Space、矢印・長押し経路を確認する。

## リスクと未解決点

- `timer(item, now)` でrunningとdoneが切り替わる瞬間のタップでは、画面が算出した状態とサーバーの処理時刻がずれる可能性がある。移動commandは既存どおりタイマー開始情報を保ち、モデルの版数・generation保護と短いUI再判定で競合時の誤移動を避ける。
- UIの表示状態から操作が確定するまでに盤面が更新される可能性がある。事前検査に加えて共有モデル検証を必ず通し、失敗理由を見えるようにする。
- 既存のmoveモデル自体はblank/doneでもmove可能であり、今回の状態制限は自動移動を発火するtap経路に適用する。既存の長押しドラッグや外部move APIの状態制限は今回の依頼範囲に含めない。
- 上段が埋まっている場合、タップは下段に留まる。自動で横移動や別鉄板への振替は行わない。
