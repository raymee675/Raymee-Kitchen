# 冷蔵庫生地24個の20分配置タイマー計画

作成日：2026年10月9日　｜　改訂日：2026年10月10日　｜　状態：Pages版の実装計画。未実装。初回開始方法は確認済み、期限超過時の配置と配置Undoは回答待ち。

この計画は生地タイマー機能の要件と検証予定を定めます。現在の利用・サポート範囲は[固定1台のスマートフォンで使うGitHub Pages構成](single-phone-github-pages-architecture.md)に従います。文書一覧は[docs索引](README.md)、Pagesでの操作と制約は[アプリREADME](../cooking-app/README.md)を参照してください。

## 目的と期待する動作

冷蔵庫から取り出した生地24個分を鉄板に配置する作業を、20分のタイマーと残数で管理します。消費数に加えるのは、新しいお好み焼きの配置がPagesのモデルで検証され、ブラウザー保存へ成功した時だけです。待機楕円の加熱開始、温度変更、移動、回収、完成ボックス操作では数を変えません。

- 最初のセットは利用者が「生地を取り出す」を押した時に開始します。この開始方法は確認済みです。押下後、保存が成功した時刻を開始時刻とし、期限を20分後にします。開始前の新規配置は受け付けません。
- 計測中は残り時間と配置済み数 `n/24` を表示します。成功した新規配置だけnを1増やします。空きマス、ID上限、期限などの検証に失敗した配置では状態を変更しません。
- 期限内に24個目の配置が成功した場合は、その保存時刻を`completedAt`として保持し、24/24と「生地リセット」ボタンを表示します。完了状態は期限経過後も維持します。
- 「生地リセット」ボタンを押すと、新しい生地セットを冷蔵庫から取り出したものとして次セットの計測を開始します。既存の全盤面「リセット」とは別操作です。生地タイマーと残数を初期化しますが、盤面、完成ボックス、実行記録、配置IDの高水位は保持します。
- 生地タイマーは既存の固定90秒加熱タイマーと完成ボックスの30分タイマーから独立させます。バックグラウンドで常時動くジョブは追加せず、保存した絶対時刻から表示状態を導出します。
- 全盤面「リセット」は現行の消去範囲を維持し、生地状態も未開始へ戻します。

## Pages版の状態と境界

生地状態は保存値とスマートフォンの現在時刻から導出します。24個目の成功だけは完了時刻を保存し、完了済みセットを期限超過と取り違えないようにします。

| 状態 | 保存状態 | 新規配置 | 表示 |
| --- | --- | --- | --- |
| 未開始 | `doughBatch=null` | 拒否 | 「生地を取り出す」 |
| 計測中 | 配置済み0〜23個、現在時刻が期限以下 | 他の配置条件を満たせば許可 | 20分タイマーと残数 |
| 期限超過 | 配置済み0〜23個、現在時刻が期限より後 | **推奨は拒否。回答待ち** | 期限超過を文字でも表示 |
| 完了 | 24個、`completedAt`あり | 現セットへの追加を拒否 | 24/24と「生地リセット」ボタン |

期限内の境界は保存時刻 `now <= deadlineAt` とする案です。画面の残り時間を秒単位で丸めても、配置可否は表示文字ではなく保存操作時の時刻で判定します。時計だけでは保存を書き換えず、再表示・復帰時に端末時刻から状態を再計算します。端末時計が大きくずれている場合の完全な補正は範囲外です。

期限超過後に残数がある場合の扱いは未決です。推奨は新規配置を止め、期限超過を表示することです。残りを廃棄して次セットを始める救済操作を加える場合は、通常の24個完了後の次セット開始とは別に要件を決めます。

## 現在のPages実装に関する確認事項

- 配置IDは成功順に採番され、1〜192の範囲が`1-1`〜`8-24`に対応します。通常の回収・提供後も実行記録がIDを保持するため、盤面上の件数から生地消費数を復元できません。最新配置のUndoだけ、既存のID再利用条件を満たす場合に番号を戻せます。
- 新規配置は各鉄板の下段の空きマスに限られます。鉄板はそれぞれ6マスなので、24個を一度に置く仕様ではありません。配置の失敗時にID採番や生地数を進めません。
- Pages保存は`localStorage`の既存キーを使い、現在の保存形式は`schemaVersion: 6`です。`use-kitchen-local.ts`はWeb Locksと`mutationQueue`で同じ保存領域の読み込み・更新を直列化し、保存後の状態を画面へ反映します。
- 同じoriginの複数タブは同じ保存領域を使います。ロックと状態前提を使って古い画面からの変更を防ぎます。この機能計画はスマートフォン1台・1ブラウザー用であり、別のスマートフォンやブラウザーとの共有・競合処理を要件にしません。
- 時刻はPagesを動かす端末の時計が基準です。画面表示は可視中のtickと復帰時の再読込で追いつかせます。画面ロック中の毎秒更新、音、通知は保証しません。
- `kitchen-model.ts`と`app/kitchen.tsx`はリポジトリ内で共通コードとして使われています。必要な変更は既存ソースの型整合性を保ちますが、legacy PC runtimeの動作保証やサポート追加はこの計画に含めません。
- Pages版には「データ管理」からのJSONバックアップ保存・検証付き復元が既にあります。現在の封筒は`format: "teppan-timer-pages-board"`、`formatVersion: 1`で、その`board`にschema 6のSnapshotを含みます。生地状態を追加する場合はJSONバックアップへ`doughBatch`を含め、書き出し・読み込み・破損データからの復旧でもタイマーと残数を失わないようにします。CSVは完了済み実行記録のみです。

## 保存データと操作契約

Snapshotと保存状態に`doughBatch: DoughBatchState | null`を追加します。`null`は未開始を表し、現在のセットだけを保存します。

| field | 型・意味 |
| --- | --- |
| `batchId` | セット開始ごとのUUID。開始コマンドのoperationIdを使う案 |
| `setNumber` | 1〜8。配置IDのMに対応 |
| `startedAt` | Pages保存処理が確定した開始時刻。epochミリ秒 |
| `deadlineAt` | `startedAt + 1,200,000`ミリ秒 |
| `placedIds` | このセットで成功した配置IDを成功順に保持。最大24件 |
| `completedAt` | 24個目の成功時刻。それ以外は`null` |

消費数は`placedIds.length`、残数は`24 - placedIds.length`から求めます。盤面数や実行記録から推測せず、同じ意味の`consumedCount`は重複保存しません。通常回収・提供では`placedIds`からIDを取り除きません。

読込時の検証では、UUID、setNumberの範囲、安全な整数の時刻、期限が20分後であること、IDの一意性・順序を確認します。配置IDのMはセット番号に一致し、次のID序数は`(setNumber - 1) * 24 + placedIds.length + 1`と整合する必要があります。24件未満では`completedAt`をnullとし、24件では`startedAt <= completedAt <= deadlineAt`を要求します。

| 操作 | 保存状態に対する前提 | 成功時の変更 |
| --- | --- | --- |
| `doughStart` | 期待するbatch IDがnull、未開始、次のIDが当セットの先頭、ID上限未到達 | 新batch、開始時刻、20分の期限、空の`placedIds`を保存。盤面世代を進め、生地開始前のUndo履歴全体を消去 |
| `create` | 期待するbatch IDと次ID序数が現状態に一致、期限内、配置済み23件以下 | 既存の配置検証に成功した場合のみ、配置・採番・`placedIds`をまとめて更新。24件目では`completedAt`も設定 |
| `doughReset`（「生地リセット」） | 期待するbatch IDが現状態に一致、24件完了、次セットのIDが存在 | 新しい生地セットを取り出したものとして、新しいbatchを20分・0/24で開始。盤面世代を進め、前セットのUndo履歴全体を消去 |
| 全盤面`reset` | 現行のgeneration前提と確認操作を通過 | 現行の消去対象を初期化し、`doughBatch=null`にする |

全操作は保存処理内で最新状態を再読込・検証し、完全な状態を書き込んでから成功として画面に反映します。書込失敗時は配置、消費数、ID、時刻のいずれも確定しません。既存の`expectedGeneration`等の前提条件は維持します。新規配置には画面が観測した`expectedDoughBatchId`と`expectedNextPancakeOrdinal`を明示し、保存時に最新値へ補完しません。生地開始・生地リセットは盤面世代を進め、古い画面のpointer操作・盤面更新を拒否します。

生地セット境界ではUndo履歴全体を消去します。開始前または前セットに属する配置・移動・削除等のUndoを次セットへ持ち越しません。特に前セット最後の配置Undoが次セット開始後に`nextPancakeOrdinal`を巻き戻すと、`setNumber`、`placedIds`、次の配置IDの整合が崩れるためです。これまでの盤面・実行記録・完成ボックス・ID高水位は保持しますが、Undo可能な操作だけを境界で確定します。

### 二重操作と競合への対処

Pagesには永続operation receiptがないため、再試行を含めたexactly-once処理は保証しません。Web Locks、既存の`mutationQueue`、メモリー上の送信中抑止に加え、batch ID・世代・採番序数の状態前提を使います。開始済みの状態に対する古い開始、完了前提が合わない次セット開始、既に進んだ採番序数を持つcreateは拒否し、状態を二重更新しません。

保存結果が不明な操作を別のoperationIdで自動再送しません。画面は最新の保存状態を読み直し、反映済みかを確認してから次の操作を促します。同じブラウザー保存領域の複数タブに関する話であり、別端末間の競合や同期を意味しません。

## 旧Pages保存形式の移行

Pagesの保存schemaを6から7へ上げます。schemaVersion 1〜6は、既存の楕円、実行記録、完成ボックス、Undo、次ID序数を保ったまま`doughBatch=null`を補います。過去のIDや盤面から消費数・開始時刻を推測しません。schemaVersion 7でfieldが欠落・不正な場合は旧形式として扱わず、保存データエラーを表示して既存データを空盤面で上書きしません。

次IDがセットの先頭に一致する場合は明示開始できます。途中のM-Nから始まる既存状態で、残りのIDを飛ばすか、IDと生地セットの対応を分けるかは未決です。自動で番号を飛ばしたり盤面を初期化したりしません。移行後も既存の盤面・記録を保ち、生地開始・新規配置を止める案を推奨します。

## 24個、採番、Undoの未決条件

新規データが`1-1`から始まる場合、先頭24回の成功配置は`1-1`〜`1-24`となり、次セットは`2-1`からです。`placedIds`は配置後の回収・提供でも保持し、実行記録と独立して現セットの消費数を示します。

期限超過で一部だけ配置した後に次セットを開始すると、現行の連番では次セットのIDが前セットのM-N範囲から始まる可能性があります。セットごとにM-1〜M-24を揃えるため未使用番号を飛ばす仕様は決まっていません。残量の救済、番号の進め方ともに明示決定までは自動変更しません。

**配置Undoの消費数への影響は回答待ちです。** 推奨案は、現セットの`placedIds`末尾がUndo対象のcreate IDと一致し、既存の最新ID再利用条件も満たす時に限り、配置・序数・`placedIds`末尾を同時に戻すことです。24個目を戻す場合は`completedAt`をnullにし、開始時刻と期限を保ちます。Undo後の現在時刻が期限を過ぎていれば期限超過表示になります。IDを安全に再利用できない場合は消費数だけを戻さず、そのUndo全体を拒否する案です。この案は未決のため、実装前に確定します。

8セット目のID上限は`8-24`です。24個完了後の次セット開始と192個の上限との関係も確認事項です。9セット目を追加したりIDを1-1へ周回したりしません。全盤面リセットを生地リセットの代用にしません。

## UIと操作案

- 共通画面の調理状況付近に生地カードを配置し、縦・横画面で既存の鉄板操作を隠さないようにします。開始前は「生地を取り出す」、計測中は残り時間とn/24、期限超過は文字による警告、完了後は24/24と「生地リセット」ボタンを表示します。
- createが保存された後だけ消費数を進めます。保存中は重複押下を抑え、失敗時は確定済み表示を保って再読込を促します。全盤面リセットと生地の次セット開始は、名前と確認内容で区別します。
- pointer操作の開始時にboard generation、batch ID、次ID序数を捕捉します。同期後にいずれかが変わっていれば古いpointer操作を破棄し、保存側でも全前提を検証します。
- 未開始、期限超過、セット完了時に新しい空きマスをタップした場合は、保存側で拒否し、利用者に理由を伝えます。ボタンの無効化だけを唯一の防止策にしません。
- ヘルプに開始方法、成功配置だけを数えること、加熱90秒とは別であること、期限超過の暫定方針を記します。残数と期限状態は色だけに頼らず文字で伝えます。毎秒の読み上げ、背景音・通知、Wake Lock拡張は含めません。

## 変更対象と実装段階

変更対象はPagesのローカル保存経路と共有モデル・画面に限ります。PC専用のサーバー、SQLite、永続operation receipt、サーバー側の復元処理、WebMCPはこの機能の実装要件・受け入れ条件にしません。既存のPages JSONバックアップ・復元は維持し、新しい`doughBatch`も往復できるよう更新します。

| 対象ファイル | 予定する変更 |
| --- | --- |
| `cooking-app/lib/kitchen-model.ts` | Snapshotと共通状態遷移、入力検証、期限・完了導出、配置・Undo・全盤面resetとの整合 |
| `cooking-app/lib/local-kitchen-storage.ts` | Pages保存schema 6→7、旧形式移行、既存JSONバックアップ形式との往復、検証と読書き |
| `cooking-app/lib/use-kitchen-local.ts` | ロック・mutationQueue内でのbatch状態、保存後Snapshot、競合時の再読込 |
| `cooking-app/app/kitchen.tsx`、`cooking-app/app/globals.css` | Pages画面のカード、開始・残数・期限・完了表示、pointer前提の受け渡し、操作説明 |
| `cooking-app/README.md` | Pages利用者向けの生地操作説明 |

`kitchen-model.ts`と共通画面に変更が及ぶ場合、リポジトリ内に残るlegacyソースの型整合を壊さないよう確認します。これはPC runtimeの動作試験、運用手順、サポート対象への追加を意味しません。

1. **仕様確定**：期限超過後の配置、配置Undoで消費を戻すか、途中状態からの導入、部分消費後のセット交換、8セット目完了後の表示を確認します。推奨案から変更があれば、本計画を改訂してから実装します。
2. **共通モデル**：成功したcreateだけ消費数・IDを一体で更新し、失敗は無変更とします。完了・期限超過を時刻から導出し、Undoと全盤面resetを分けます。
3. **Pages保存**：schema 7へ移行し、保存・読込・旧schemaの移行を実装します。読み込み・保存失敗で空盤面を上書きしません。
4. **Pages hookとUI**：既存Web Locks・mutationQueueに統合し、生地カード、pointer時の期待値、エラー後の同期を接続します。
5. **Pages向け検証**：保存移行、状態前提による二重操作拒否、同一保存領域の排他、期限境界、24個目、Undo、全盤面resetを確認します。

## 受け入れ条件と今後の検証計画

- 初回の「生地を取り出す」は押下時に保存され、開始前の新規配置は拒否される。待機楕円の加熱開始では残数が変わらない。
- 配置モデルとlocalStorageへの保存が両方成功した時だけ1個を数える。容量・ID・期限・保存エラーによる失敗では盤面、ID、残数を変更しない。
- 24個目の成功で完了時刻を保存し、再読込後も24/24を保つ。完了後の時刻経過で未完了へ戻らない。
- 24個完了後だけ「生地リセット」ボタンを表示する。押すと新しい生地セットを取り出した扱いで、新しいbatch ID、開始時刻、20分の期限、0/24を保存し、盤面、完成ボックス、実行記録、ID高水位を保つ。全盤面resetとは異なる操作である。
- 最初の生地開始と「生地リセット」の各セット境界で盤面世代を進め、配置・移動・削除等を含むUndo履歴全体を消去する。旧セットのUndoや古いpointer操作を新セットへ持ち越さない。
- 古いbatch IDや次ID序数を持つ操作は拒否し、同じ保存領域を使うタブはロックと直列処理で更新する。永続receiptによるexactly-once保証は受け入れ条件に含めず、状態前提による拒否範囲を明記する。
- schema 1〜6のPagesデータから既存の盤面、記録、完成ボックス、Undo、次ID序数を保ち、生地状態を未開始で追加する。過去の消費数を推測しない。不正なschema 7はエラーとして扱う。
- JSONバックアップの書き出し・プレビュー・復元・復旧で`doughBatch`、残数、開始時刻、期限、完了状態を保つ。従来のformatVersion 1/schema 1〜6のバックアップは生地状態を未開始として扱い、その状態を復元前の確認に表示する。不正なバックアップや保存失敗は現在の盤面を置き換えない。CSV形式は変更しない。
- 既存の固定90秒、完成ボックス30分、CSV列、全盤面リセット、配置UndoのID再利用条件を変えない。生地Undoの結果はユーザー回答後に受け入れ条件へ確定する。
- 期限超過時の新規配置は回答待ちであり、推奨は拒否です。部分セットや8セット目の扱いも、決定前に実装済みとは扱いません。

実装後はPagesの保存移行・状態遷移・同一保存領域の競合を対象にしたテストを計画し、`cooking-app/`から`npm run typecheck`と`npm run build:pages`を行います。画面では開始、成功・失敗配置、期限前後、24個目、再読込、次セット、Undo、全盤面reset、保存失敗、キャッシュ後のオフライン再起動、調理中の更新保留を確認します。期限の直前・同時刻・直後を含めます。これは将来の検証計画であり、この文書改訂ではテスト、型確認、ビルドを追加・実行していません。

## 未決事項とリスク

1. **期限超過後の配置（回答待ち）**：警告のみで継続するか、配置を止めるか。推奨は、配置済み0〜23個なら新規配置を止め、残りを廃棄して次セットへ進む操作は別途定義することです。
2. **配置Undo（回答待ち）**：セット内では、最新配置の既存ID再利用条件を満たす場合に消費数も戻すことを推奨します。24個目をUndoしたら完了を解除し、元の開始時刻・期限を維持します。生地開始・生地リセット時は移動を含むUndo履歴全体を消去する境界案を採用し、過去セットのUndoを許しません。
3. **途中導入と部分消費**：過去の取り出し時刻・消費履歴は復元できません。未使用IDを飛ばすか、生地セットとM-Nの対応を変えるかは未決です。盤面や採番を黙って初期化しません。
4. **8セット目の終了**：ID範囲は1-1〜8-24です。上限後の次セットの表示と操作を決めます。IDの周回・9セット目は追加しません。
5. **端末時計とタブ停止**：Pagesは端末時計を使います。非表示・ロック中の毎秒更新や通知は保証せず、復帰時に保存した絶対時刻から追いつかせます。
