# 冷蔵庫生地24個の20分配置タイマー 計画

作成日：2026年10月9日　｜　状態：計画作成・独立レビュー済み。実装前。初回開始方法は確認済み、期限超過・配置Undoは回答待ち。

## 目的・期待動作

冷蔵庫から取り出した生地24個分を鉄板へ配置する作業を、20分のタイマーと残数で管理する。消費として数えるのは、新しいお好み焼きの配置をモデルと保存先が受け付けた時点である。待機楕円の加熱開始は別操作であり、配置数を増やさない。

- 最初のセットは、ユーザーが「生地を取り出す」を押した時に開始する。この開始方法はユーザー回答で確定した。ボタンを押した保存時刻を開始時刻とし、期限を20分後にする。開始前の新規配置は受け付けない。
- セット中は「配置済み n/24」と残り時間を表示する。新規配置が成功した場合に限りnを1増やす。位置、容量、ID上限、期限などの検証で配置が失敗した場合は数えない。
- 20分以内に24個目の配置が成功した時刻をcompletedAtとして保存し、「24/24」と「生地リセット」ボタンを表示する。完了後は時計が期限を越えても完了状態を期限超過へ戻さない。
- 「生地リセット」は既存の全盤面「リセット」と別の操作である。押すと新しい生地24個分を取り出した扱いになり、時刻を20:00へ戻し、配置済み0/24・残り24個の次セットを開始する。鉄板、完成ボックス、実行記録、配置IDカウンターは消去しない。既存ID上限に達する8セット目の次の開始は確認事項とする。
- 例：開始後、配置成功ごとに1/24、2/24…と進み、期限内の24個目で完了する。次セット開始後は同じ盤面を保ったまま0/24へ戻る。
- 生地タイマーの期限超過と、90秒加熱タイマー・完成ボックス30分タイマーを混同しない。背景で動き続けるジョブを追加せず、保存した絶対時刻から表示状態を計算する。
- 既存の全盤面リセットは別に残す。そちらが確定した場合は、現行どおり盤面・完成ボックス・記録・Undo履歴を消し、IDを1-1へ戻すとともに、生地状態も「未開始」に戻す。

## 状態と境界の推奨案

タイマー状態は保存値と現在時刻から導出する。完了だけは24個目の成功時に保存し、後から期限超過と取り違えないようにする。

| 状態 | 保存データの意味 | 新規配置 | UI |
| --- | --- | --- | --- |
| 未開始 | 開始時刻・期限なし、配置済み0 | 拒否 | 「生地を取り出す」 |
| 計測中 | 配置済み0〜23個、現在時刻が期限以下 | 通常の鉄板検証を通れば許可 | 20分カウントダウン、残数 |
| 期限超過 | 配置済み0〜23個、現在時刻が期限より後 | **推奨：拒否**。回答待ち | 期限超過の表示。通常の「生地リセット」は出さない |
| 完了 | 24個、completedAtが期限以下 | 現セットの追加配置は拒否 | 24/24と「生地リセット」 |

期限境界は、配置コマンドを保存先が適用する時刻で判定し、推奨境界を「成功時刻 <= deadlineAt」とする。deadlineAtと同時刻までは期限内、それより後は期限超過として扱う。画面の残り秒表示はceilで丸めるため、表示が00:00でも操作可否は表示文字列では判定せず、保存先の時刻で判定する。24個目の成功時刻completedAtは、そのcreateを保存したトランザクション内で確定し、pointer押下時刻や通信開始時刻を使わない。

期限を過ぎて残数がある場合の扱いは未確定である。通常の「24個消費後の生地リセット」と混ぜない。推奨は新規配置を止め、期限超過を明示し、別途「残りを廃棄して次セットを始める」等の救済操作を要件確認後に設計すること。警告だけで作成を続ける案では、20分を超えた生地の配置を許し、24個目到達時の通常リセット条件も定義し直す必要がある。

## 現行コードで確認した事実と制約

- **採番は配置成功順**：cooking-app/lib/kitchen-model.ts の pancakeIdForOrdinal は1〜192の序数を 1-1〜8-24 に変換する。Mは1〜8、Nは1〜24で、24個ごとにMが進む。applySnapshotCommand の create が配置制約を通過した後に nextPancakeOrdinal からIDを払い出し、カウンターを進める。start は別のコマンドである。
- **IDカウンターは盤面数ではない**：通常の完成・取り出し後もExecutionRecordにIDが残り、IDカウンターは巻き戻らない。従って鉄板上の件数、完成ボックス件数、現在存在する最大IDのどれからも、現在の生地消費数は復元できない。配置Undoは最新の配置で、同じIDの楕円・完成項目・記録が残らない等の条件が揃った時だけIDを再利用する。通常の回収・提供操作はIDを再利用しない。
- **盤面上の制約**：新規配置は鉄板の下段の空きマスだけで、鉄板は各6マスである。全24個を同時に置ける設計ではなく、既存の調理・移動・完成ボックス操作を続けながら空いた下段へ配置する。配置がグリッド容量や空きマスで失敗した時にカウンターと消費数を進めてはならない。
- **UIと直接操作経路**：PCとPagesは共通の cooking-app/app/kitchen.tsx を使う。空きマスのpointer-upから create を送る経路に加え、PC版は同画面がWebMCPの operate_kitchen に create を公開する。どちらも同じ共通モデルへ到達するため、UIの無効化だけでなくモデル側で未開始・期限超過・完了を拒否する必要がある。HTTPは既存の /api/board POSTを使い、新しい作成APIは不要。
- **PC保存**：cooking-app/server/storage.mjs は BEGIN IMMEDIATE 内でコマンド、operation receipt、revision、SQLite boards.state JSONを更新する。SQLiteの表スキーマを変更せず、状態JSONへタイマー情報を追加できる。状態は旧配列・既存envelopeを共通正規化して読む。
- **Pages保存**：cooking-app/lib/local-kitchen-storage.ts は既存localStorageキーを使い、現在のschemaVersionは6。cooking-app/lib/use-kitchen-local.ts はWeb Locks、単一編集タブ、mutationQueueによって読込・保存を直列化する。PagesにはPCのような永続operation receiptはない。in-memory pendingによる同時送信抑止と、タイマー状態・batch IDの前提条件を使う。新たな汎用receipt表は追加しない。
- **Snapshotの組み立て箇所**：PCはサーバーの正規化状態を readSnapshot から返し、コマンド保存時に保存JSONの各fieldを列挙する。Pagesは readLocalBoard と writeLocalBoard に加え、use-kitchen-local.ts のコマンド後Snapshotを個別に組み立てる。新fieldはこれら全箇所で往復させる。PCの use-kitchen.ts はAPI Snapshot全体を受理するが、server側のJSON保存には明示的なfield列挙がある。
- **時刻表示**：PCの use-kitchen.ts はサーバー時刻と応答遅延から補正した currentTime() を持ち、約100msごとに表示を更新する。Pagesは端末 Date.now() と可視時のtick、復帰時のlocalStorage再読込を使う。期限はepochミリ秒の開始・期限として保存し、残り秒はUIで導出する。
- **バックアップ・復元**：cooking-app/server/restore.mjs は復元前後にboard stateを検証する。新fieldの形式・数値範囲・相互関係をここにも渡し、現在形式のバックアップから残数・開始時刻・期限・完了時刻を失わず復元する必要がある。
- **既存リセット**：現在の reset Commandは盤面全体を消してIDを1-1へ戻し、generationを進める。生地リセットへ流用してはならず、新コマンドまたは明確に異なる操作契約を設ける。
- **実行記録**：加熱開始、温度履歴、回収、提供結果は既存ExecutionRecordとCSVが保持する。生地消費は新規createにだけ結び、start、move、adjust、回収・提供では増減しない。各ExecutionRecordへ生地セット番号を追加する要件は現時点にないため、CSV・履歴形式の変更は今回の範囲に含めない。
- **画面点灯**：Pages版のWake Lockは現在、90秒タイマーが動作中の楕円がある時だけ要求する。生地だけ計測中の画面消灯抑止は本計画の追加対象にしない。背景停止中の音・通知は既存機能にない。

## データ・コマンド設計案

以下は未回答事項に推奨案を採用した場合の具体的な実装契約である。回答が異なる場合は、実装前にこの契約と受け入れ条件を改訂する。

### 保存する生地状態

Snapshotと正規化済みboard stateに `doughBatch: DoughBatchState | null` を追加する。nullは未開始を意味する。現在セットだけを保存する。

| field | 型・意味 |
| --- | --- |
| batchId | 開始操作のoperationIdを使うUUID v4。生地交換ごとに異なる識別子 |
| setNumber | 1〜8。対応するお好み焼きIDのM |
| startedAt | 保存先で確定した取り出し時刻。epochミリ秒 |
| deadlineAt | startedAt + 1,200,000ミリ秒 |
| placedIds | このセットで成功した配置IDの配列。配置順で最大24件 |
| completedAt | 24個目成功時のepochミリ秒。それ以外はnull |

消費数は `placedIds.length`、残数は `24 - placedIds.length` から求める。盤面や実行記録から数え直さず、重複するconsumedCountも保存しない。最大24件のID配列により、配置Undoの対象が現セットに属するかを判断できる。通常回収・提供でIDをこの配列から取り除かない。

正規化・復元検査では、UUID、Mの範囲、有限かつ安全な整数の時刻、20分の時刻差、IDの一意性と配列順を検証する。i番目の配置IDは `M-(i+1)` と一致し、`nextPancakeOrdinal = (M-1)*24 + placedIds.length + 1` を満たすこと。24件未満ならcompletedAtはnull、24件なら `startedAt <= completedAt <= deadlineAt` が必須である。完了時のplacedIdsも保存するため、完了後に元の楕円が盤面から消えても判定を保てる。

### 操作契約と原子的な更新

| Command | 生地の前提条件 | 成功時の更新 |
| --- | --- | --- |
| doughStart | expectedDoughBatchId=null、未開始、次IDがM-1、ID上限未到達 | 新batchId・M・開始時刻・期限、placedIds=[]、completedAt=null |
| create | expectedDoughBatchIdが現batchId、expectedNextPancakeOrdinalが現カウンター、期限内、配置済み23件以下 | 既存配置検証後、楕円・採番カウンター・placedIdsを同時更新。24件目でcompletedAtを設定 |
| doughReset | expectedDoughBatchIdが現batchId、期限内完了済み、次Mが存在 | M+1の新セットを20:00・配置済み0/24で開始 |
| reset（既存の全盤面初期化） | 現行のgeneration検証と確認操作 | 現行消去範囲に加えてdoughBatch=null |

全操作で既存operationIdとexpectedGenerationの契約を維持する。新しい生地操作とcreateの生地識別子、およびcreateのexpectedNextPancakeOrdinalは画面が観測した値を明示送信し、送信時に最新値へ暗黙補完しない。古いbatch IDの遅延createは次セットへ適用せず、状態競合として最新Snapshotの取得を促す。同一セット内でも採番カウンターの前提を照合し、Pagesで完了済みcreateを再送してもう一個として数えない。位置・容量・ID・生地のいずれかの検査で失敗した場合は、楕円、消費数、採番、時刻を一切変更しない。

開始・次セット開始ではUndo履歴全体を空にする。過去セットのcreateだけを部分選別せず、移動履歴も含めてこの操作を取り消しの境界とする。盤面・完成ボックス・実行記録は保持する。この二つの生地操作ではboard generationを増やさず、batchIdでセットの変更を識別する。全盤面resetと配置Undoの既存generation更新は維持する。

PCは既存SQLiteトランザクションに全更新とoperation receiptを含める。同operationIdの再送は既存receiptで処理し、タイマーを再開始しない。23件時の同時createは一件だけを24件目として受け付ける。PagesはWeb Lock・mutationQueue内で一つの状態として書き込み、永続receiptの代わりに未開始／完了済みの前提とexpectedDoughBatchIdの照合で二重開始を拒否する。両hookのpending key分類に、idを持たないdoughStart/doughResetを追加する。

採番前提の照合により、同じSnapshotから別端末が同時配置した場合は一方が競合になる。競合側は再同期して操作をやり直す。成功している可能性がある操作へ、新しいoperationIdを自動発行して再送しない。この操作上の変更はREADMEとエラー文で説明する。PCで同operationIdの通信再送を行う既存経路は維持する。

旧PCコマンドのreceipt照合を壊さないよう、パーサーは生地識別子と採番前提のない旧createも元の形で読み取れるようにする。ただし新たに適用するcreateには両方を必須とし、旧画面の新規配置は更新を促して拒否する。過去に適用済みの同operationId再送はreceipt経路のまま処理する。

### 旧保存形式の移行

PagesはschemaVersion 7へ更新する。version 1〜6とPCの旧状態・バックアップにはdoughBatch=nullを補い、既存の位置・加熱時刻・記録・ID・Undoを保持する。取り出し時刻を導入時刻として自動登録しない。新schema 7でfieldが欠落・不正な場合は旧形式と扱わず、保存データのエラーにする。PCは新JSON envelopeに `doughSchemaVersion: 1` を保存し、旧形式のfield欠落と新形式の欠損を区別する。新marker付き状態ではdoughBatchが明示的なnullまたは有効な状態であることを要求し、restoreでも同じ検証を通す。

次IDがM-1であれば、新しい生地を取り出す操作で追跡を開始できる。既存データがM-Nの途中なら、暫定案では自動的に新24個を割り当てず、開始と新規配置を止めて導入方法の判断を待つ。既存楕円の加熱・移動・回収・記録出力は利用できる。既存生地を新しい20分として扱ったり、未使用番号を無断で飛ばしたり、盤面を自動初期化したりしない。

## 24個とM-N IDの整合、およびUndo・削除

既存のIDは「ボード全体の配置順」であり、常に生地セット番号を表すfieldではない。IDが1-1から始まる新規状態なら、最初の24配置は1-1〜1-24、次の24配置は2-1〜2-24となる。途中導入で次IDが例えば3-1なら、生地追跡もM=3から始める。生地カウントはID最大値から求めず、現セットの配置IDを独立して保存する。配置済み楕円が通常回収で盤面からなくなっても、そのIDは消費済みとして残す。

期限超過後に15個で中断して次の生地セットを開始する場合、現行採番を続けるだけでは次セットのIDは 1-16 からとなり、24個がM境界をまたぐ。セットごとに M-1〜M-24 を対応させるには、未使用Nを飛ばして次Mへ進める別ルールが必要になる。既存ID仕様を保持する本計画では、救済操作を通常の生地リセットへ混ぜず、残量の扱いと番号の進め方が決まるまで自動変更しない。

配置Undoの生地数への影響は未回答である。推奨は、現セットのplacedIds末尾とUndo対象のcreate IDが一致し、既存のID再利用条件を満たす場合に、配置・採番・placedIds末尾を同時に戻すこと。24個目をUndoする場合はcompletedAtを消し、開始時刻・期限を維持して配置済み23/24・残り1個へ戻す。Undo後の現在時刻が期限より後なら期限超過になる。IDを再利用できない例外では、生地数だけを戻してM-N対応を崩さず、当該Undo全体を拒否する。現セットに属さない移行前のUndoでは、生地状態を変更しない。既存のgeneration更新と失敗時の無変更を守る。

回答が「配置した時点で消費確定」なら、ID再利用と消費数の関係も改訂が必要になる。同じIDを再配置して二度消費した場合のID対応を未定義のまま実装しない。

通常の回収・完成ボックス提供はExecutionRecordを維持し、消費数を戻さない。現在の利用者向けUIでは盤外deleteは廃止されており、通常のremoveもID記録を残す。移行済みの旧UndoEntry/deleteデータを正規化で保全する場合も、新しい生地消費を勝手に変えない。次セット開始は前セットcreate Undoの境界となる。

## UIと操作案

- 共通ヘッダーの「調理状況」付近に生地カードを置く。縦・横画面で鉄板の主要操作を隠さない幅にする。開始前は「生地を取り出す」、計測中は残り時間とn/24、期限超過は明確な警告、完了時は24/24と「生地リセット」を表示する。
- 24個目の配置成功後にだけ完了カードへ切り替える。生地リセットの保存成功後に次セットを20:00・配置済み0/24へ更新し、送信中・接続不可では開始／リセットを無効化する。失敗時は確定済みの状態と時刻を保つ。既存全体リセットとはボタン名と説明を区別する。
- 未開始・期限超過・セット完了後に空きマスをタップした場合は、保存側の拒否をtoast等で説明する。フロントの事前disableに加え、API/モデルの拒否を必須にする。
- UI Contactにはpointer-down時のboard generationと生地batch IDを保持する。同期でいずれかが変わった時は進行中のpointer操作をキャンセルし、createには捕捉したexpectedDoughBatchIdを渡す。保存側でも識別子を照合する。
- createのexpectedNextPancakeOrdinalもpointer-down時に保持する。別端末の配置が間に入った場合は、その古い値で拒否し、消費を自動的に後続番号へ割り当てない。
- PCのWebMCP operate_kitchenにdoughStart/doughResetを公開し、createの生地識別子と採番前提を条件付き必須とする。read_kitchenとoperate_kitchenの返却値にdoughBatchとnextPancakeOrdinalを含め、取得結果を使って生地操作を実行できるようにする。既存の全体resetは同ツールへ追加しない。
- 8-24の期限内配置後も「生地リセット」の表示条件は満たす。ただし暫定案ではID上限を理由に無効化し、9セット目を開始しない。これは「押すと次セット開始」という要求に対する既存上限由来の制限であり、最終仕様の確認事項とする。
- ヘルプに「生地開始は配置前」「配置成功を消費として数える」「加熱開始とは別」「期限超過時の扱い」を反映する。カードに残り時間と残数を文字で示し、色だけで期限状態を伝えない。毎秒の読み上げを避け、開始・完了・期限超過の変化を通知する。背景の音・通知やWake Lockの拡張は本計画に含めない。

## 未決事項・リスク

1. **期限超過時の新規配置（回答待ち）**：警告のみで続ける案か、配置を停止する案か。推奨は期限超過・配置済み0〜23では配置を止める。選択によって期限判定後の状態遷移と24個目の意味が変わる。
2. **配置Undo（回答待ち）**：Undoで消費数を戻す案か、配置成功時点で消費確定とする案か。推奨は成功した最新配置Undoでcountを戻す。24個目UndoならcompletedAtも解除し、元の期限は維持する。
3. **部分消費後の次セット**：期限超過した残量の廃棄・次セット開始は依頼に含まれない。救済ボタンを追加するなら別コマンド・確認文が必要。M-Nを各物理セット単位で M-1〜M-24 に揃えるか、現行の連番を続けるかも決める。現行連番を続ける場合、部分セット後のID範囲は生地セットと一致しない。
4. **M=8完了後**：24個消費後にリセット表示という要望と、現行ID上限192（8×24）との境界を解決する必要がある。9セット目IDや周回は導入しない。選択肢はID体系の別変更か、全体初期化して1-1から始める等だが、後者は盤面・記録消去を伴うため本機能に混ぜない。8セット目完了後の表示・ボタン状態を明示する。
5. **旧データ移行**：過去の取り出し時刻と正確な消費履歴は復元できない。次IDがM-1なら明示開始できる。M-N途中のデータでは新しい24個とIDグループが一致しないため、本書の暫定案は生地開始・新規配置を停止する。既存盤面・記録は保持する。この導入制約を採用するか、未使用番号を飛ばす等の明示移行を用意するかを決める。
6. **時計と画面停止**：PCはサーバー時計で補正できるが、Pagesは端末時計が基準。タブ非表示中の表示更新・音・通知は保証しない。絶対期限は保存し、復帰時に追いつかせる。
7. **Undo境界・同時配置**：本書ではセット開始／交換でUndo履歴全体を消去し、移動も含めて境界を作る。createには採番前提を追加するため、同じ状態を見た複数端末の同時配置の一方はやり直しになる。生地数・既存IDの一致を保つための設計上の取引として実装と説明に反映する。
