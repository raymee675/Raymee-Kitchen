# Pages版 生地タイマーを6個・20分に変更する実装計画

作成日：2026年10月9日　｜　改訂日：2026年10月11日　｜　状態：Pages版の6個タイマー変更を実装済み。型確認・Pagesビルド・差分チェック成功。操作シナリオの実機確認とテスト実行は未実施。

この改訂は、既存の生地タイマーを「1回6個・20分」に変更し、6個タイマーを4回実行して現在の24個単位のID範囲を消費するための実装計画です。対象とする運用は[固定1台のスマートフォンで使うGitHub Pages構成](single-phone-github-pages-architecture.md)です。旧24個タイマーの途中状態を見つけた場合は機能を停止し、利用者に盤面・完成ボックス・実行記録を含む全体リセットを促します。この扱いは利用者に確認済みです。

## 目的と期待する動作

冷蔵庫から出した生地を、1回あたり最大6個、20分以内に鉄板へ配置する。現在のID範囲（1〜192を24個ずつ区切る制約）は保ち、各24個範囲を4回のタイマー運転に分ける。新しい楕円を数えるのは、配置モデルの検証とブラウザー保存の両方が成功した場合だけとする。

- 1回の上限は6個。最初は利用者が「生地を取り出す」を押して20分を開始する。6個すべてを期限内に配置したら、現在の「生地リセット」ボタンを表示し、押下で次の6個分の20分を開始する。
- IDは24個区切り内の連続した6個ずつ割り当てる。例：1回目 `1-1`〜`1-6`、2回目 `1-7`〜`1-12`、3回目 `1-13`〜`1-18`、4回目 `1-19`〜`1-24`。次は `2-1`〜`2-6`。同じ24個範囲を5回以上使わない。
- 6個配置前に期限が過ぎたら、配置を停止する。未配置分は廃棄扱いにして、現行の「残りを廃棄して次セット開始」操作から次の6 ID区間へ進む。期限切れで配置数が0でも現在の6 ID区間全体を消費済みにする。次の区間を同じIDで再利用しない。
- 配置済み数は現タイマー区間内で数え、通常の回収・提供・盤外削除では減らさない。安全条件を満たす直前配置Undoの成功時だけ1戻す。6個目の配置をUndoした場合は完了状態を解除する。
- 初めてタイマーを開始する時点で次IDが24 ID境界の途中なら、従来どおり次の24 ID範囲の先頭まで未使用IDを飛ばす。例：次IDが `1-12` なら `2-1` から開始する。これは既存の途中導入ルールを維持するためで、1つの24 ID範囲の途中で最初の6個タイマーだけを開始しない。
- 既存上限 `8-24`（192個）と全盤面リセットの意味を変えない。次の6 ID区間を確保できない場合は開始を拒否し、理由を表示する。
- 加熱90秒・完成ボックス30分・CSVの既存動作は変更しない。常時動作するバックグラウンドジョブや通知は追加しない。

## 現行実装の確認結果と制約

- `cooking-app/lib/kitchen-model.ts` の `DOUGH_BATCH_SIZE = 24` が、タイマー1回の容量と24 ID境界の両方に使われている。`nextDoughBatchFirstOrdinal`、Snapshot正規化、開始・完了・期限交換、Undoにもこの定数が使われている。
- `DoughBatchState` は現タイマー区間の先頭序数・開始時刻・期限・配置済みentity key・完了時刻を保持する。保存された配置済みentity keyから数を導くため、楕円数や実行記録から現セット数を推測しない。
- `cooking-app/lib/local-kitchen-storage.ts` のPages保存schemaは現在9。schema 7〜9では `doughBatch` を読み込む。旧24個タイマー状態は保存データに生地区間のサイズを記録していないため、schemaVersionと配置済み数を使って識別する必要がある。
- Pages画面の表示・警告・バックアッププレビューは `DOUGH_BATCH_SIZE` と「24個分」の文言を直接参照している。`cooking-app/README.md` と計画書にも旧容量が書かれている。
- `use-kitchen-local.ts` は保存形式エラー時に編集を停止し、元データを上書きしない。現状の復旧は検証済みJSONバックアップを読み込む方法で、Snapshotが読めない場合は既存の全体リセットボタンを実行できない。したがって、旧タイマー検出時は専用のブロック状態と、Snapshotを読めなくても使える明示確認付き全体リセット経路が必要。
- 盤面操作はWeb Locksと`mutationQueue`で直列化し、保存後のSnapshotを画面へ反映する。開始・作成・Undo・期限交換・リセットの前提条件とID高水位を保持する。Pages以外のPC runtime/APIに生地機能を追加しない。

## 状態、採番、移行の設計

タイマー容量と既存ID境界を別の定数として扱う。例として `DOUGH_TIMER_BATCH_SIZE = 6` と `DOUGH_ID_BLOCK_SIZE = 24` を置き、24境界への丸め、6個区間の長さ、残数表示がそれぞれ正しい定数を使うようにする。`DOUGH_BATCH_SIZE` のように意味が曖昧な既存参照を残さない。

| 状態 | 生地区間 | 新規配置 | 次の操作 |
| --- | --- | --- | --- |
| 未開始 | `doughBatch=null` | 拒否 | 「生地を取り出す」。開始先頭は24 ID境界に揃える |
| 計測中 | 0〜5個を記録、`now <= deadlineAt` | 他の配置検証も通れば許可 | 6個完了で「生地リセット」 |
| 期限超過 | 0〜5個、未完了、`now > deadlineAt` | 拒否 | 現6 ID区間を破棄扱いにして、次区間から開始 |
| 6個完了 | `placedEntityKeys.length=6` と `completedAt` | 現区間への追加を拒否 | 「生地リセット」で次の6個区間へ |
| 旧24個タイマー停止 | schema 7〜9の有効な未完了旧batch | 全ての盤面操作を停止 | 明示確認後に全体リセットのみ許可 |

`doughBatch.firstPancakeOrdinal` は各6 ID区間の先頭を指す。新しい区間は完了・期限超過のどちらでも `firstPancakeOrdinal + 6` とする。各区間は24 ID境界を跨がない。初回・状態なし開始では次の24 ID境界に揃え、`nextPancakeOrdinal` と6 ID分の上限を保存時に確認する。配置と残数の更新は現在のモデル同様に一つの保存操作で行う。

Pages保存schemaは9から10へ上げる。schema 1〜6には生地状態がないため、盤面・実行記録・完成ボックス・Undo履歴・次IDを保ったまま未開始状態を補う。schema 7〜9のうち、正しく完了した旧24個区間（24件かつ`completedAt`あり）は旧24個範囲を消費済みとして扱い、`doughBatch=null`に変換する。IDと他の記録は維持し、次回は次の24 ID境界から開始する。

schema 7〜9の旧区間が未完了（配置済み0〜23個、active/expiredを問わない）の場合は、新仕様へ読み替えず、専用の `legacy-dough-reset-required` エラー状態にする。保存元JSONをそのまま保護し、表示・新規配置・移動・削除・Undo・生地操作・バックアップ復元を含む通常編集を停止する。画面に旧仕様の途中状態を検知した旨と、盤面・完成ボックス・実行記録・Undo履歴・IDをすべて消去して `1-1` から再開することを明記し、「全体リセット」からさらに明示的な確認を経たときだけ空のschema 10へ置き換える。エラー検出直後の自動初期化、未確認のリセット、通常エラーの包括的なリセット許可は行わない。

リセット処理は専用のhook/storage経路に置く。編集ロック下で保存元データを再確認し、ブロック状態の検出時に捕捉した元データから変更されていない場合のみ全消去を確定する。更新・保存領域の書き込みに失敗した場合は旧JSONを保持し、操作停止状態を維持する。これにより読めないSnapshotが原因で既存リセットボタンが無効になる穴を塞ぐ。

JSONバックアップも新しい6個状態を検証・往復できるようにする。schema 7〜9の未完了24個タイマーを含むバックアップは復元を拒否し、現在の盤面を変更しない。schema 7〜9の完了済み24個batchを含むバックアップは、保存データと同じ規則で未開始へ変換する。CSV形式は変更しない。

## 操作と保存の契約

| 操作 | 前提 | 成功時 |
| --- | --- | --- |
| `doughStart` | 未開始、期待するgeneration・batch ID・次IDが一致。24境界から6 ID確保可能 | 6 ID区間、開始・期限時刻、空の配置済みkeyを保存。既存のセット境界のUndo消去を維持 |
| `create` | 現batchと次IDの前提が一致、未完了・期限内・5件以下 | 楕円・ID高水位・配置済みkeyを同一保存で更新。6件目だけ`completedAt`を設定 |
| `doughReset` | 現区間が6件完了、次6 ID区間を確保可能 | `firstPancakeOrdinal + 6` から新しい20分区間を保存 |
| `doughDiscardAndStart` | 現区間が期限超過・未完了、次6 ID区間を確保可能 | 現在の6 ID区間全体を消費済みにし、`firstPancakeOrdinal + 6` から新しい20分区間を保存 |
| createの`undo` | Undo対象keyが現batchの末尾で、既存のID再利用条件も満たす | 楕円・ID序数・配置済みkey末尾をまとめて戻す。6個完了を取り消すと完了時刻を消す |
| 全体`reset` | 通常状態では既存generation条件。旧24個batch検出時は特別なブロック状態と保存元照合、確認操作が成功 | 楕円・完成ボックス・記録・Undo・生地状態を全消去し、次IDを`1-1`へ戻す |

全ての通常操作は最新Snapshotをロック下で確認し、保存に成功するまで成功表示や残数を進めない。期限の境界は保存処理内の `now <= deadlineAt` とする。期限表示文字ではなく保存時に判定する。画面の表示・pointerガード・保存側検証を整合させ、古い画面からの操作をgeneration、batch ID、次IDの前提で拒否する。

## 受け入れ条件

- 空盤面から4回続けて完了すると、それぞれ6個で20分が計測され、ID範囲が `1-1〜1-6`、`1-7〜1-12`、`1-13〜1-18`、`1-19〜1-24` になる。次の区間は `2-1〜2-6` である。
- 6個目の保存成功時だけ完了扱いとなる。残数表示は0〜6の範囲で正しく、6個より多く配置できない。失敗した配置は盤面・ID・残数を進めない。
- 期限超過後の配置を保存側でも拒否する。残りを廃棄して次を開始すると、配置数に関わらず現6 ID区間を飛ばして`+6`から再開する。4区間目後は次24境界へ進み、IDを再利用しない。
- 初回の次IDが24 ID境界の途中なら次の24境界から開始し、飛ばすIDを操作前に説明する。次の6 IDを確保できなければ開始・交換しない。
- 回収や盤外削除では現batch消費数を減らさない。安全条件を満たした直前配置Undoだけが消費数を戻す。
- schema 1〜6の既存データはデータを保ったまま未開始へ移行する。schema 7〜9の未完了旧batchはエラーで全機能が停止し、利用者の明示確認がない限り保存値を変更しない。エラー画面からの全体リセットは盤面、完成ボックス、記録、Undo、生地状態を消し、IDを`1-1`へ戻す。
- schema 7〜9の完了済み24個batchは消費済みIDと他のデータを保って未開始へ移行する。以後の新しいタイマーを6個区間で始める。
- 6個状態のJSONバックアップを保存・プレビュー・復元できる。未完了旧batchを含むバックアップは拒否し、現在データを変更しない。CSV列は変更しない。
- 加熱90秒、完成ボックス30分、盤面操作、ID上限192個を回帰させない。Pages以外の実装範囲を増やさない。

## リスクと扱い

- **旧未完了batchでの全面停止**：利用者が全体リセットを確定すると既存の盤面・履歴・実行記録は消去される。確認UIに消去対象を明示する。自動変換や自動消去はしない。
- **schema 7〜9の完了batch判定**：24件すべてと有効な`completedAt`が揃う場合だけ安全に移行する。それ以外は未完了または不正として停止し、データを保護する。
- **区間末尾の期限切れ**：期限切れ区間も6 IDを消費するので、4回のタイマー運転は各24 IDブロック内の4区間に対応する。配置に使われなかったIDを後で詰め直さない。
- **ID上限**：最終24 ID範囲の途中で次6個分を確保できなくなったら次のタイマーを止め、既存どおり上限を表示する。ID周回や既存記録の書き換えはしない。
