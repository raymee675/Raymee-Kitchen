# 鉄板3×2セル配置 計画

作成日：2026年10月4日　｜　状態：実装中。過密データは利用者の手動整理後に移行

## 目的・期待動作

各鉄板を3列×2行、計6セルに分け、各セルに楕円を1個だけ配置する。楕円の中心は常にセル中央に固定し、既存サイズの約1.15倍にする。SVG座標は1600×900、正規化座標は0〜1。セル中心はx={1/6, 1/2, 5/6}、y={1/4, 3/4}とする。楕円の幅・高さを線形に各1.15倍してもセル内に余白を確保できる見込みで、境界と温度矢印を含めてUIで確認する。

空きセルのタップはその中心に配置する。楕円の長押しドラッグは離した先に最も近いセルへスナップし、占有済みセルなら移動を拒否する。移動・配置は既存Undoで戻せる。鉄板外/隙間へのreleaseはキャンセルし、元のセルに残す。

## コード調査で確認した現状・制約

- cooking-app/app/kitchen.tsxの空き位置tapは実座標でcreateを送り、dropTargetAtはドラッグ点を座標へ変換し、overlapsで衝突判定する。SVGに長押しとpointer captureがある。
- cooking-app/lib/kitchen-model.tsのPancake.x/yは0〜1の自由座標で、楕円サイズはOVAL_RX=0.07875、OVAL_RY=0.095。applySnapshotCommandのcreate/moveとUndo move復元も自由座標・楕円overlap基準。UndoEntry.move.fromは操作前の鉄板とx/yを保存し、create Undoは作成項目を取り除く。
- 盤面SVGは1600×900、CSS .plate は16:9。新しいセル間隔は横1/3、縦1/2となる。
- SQLiteボードJSONとPages localStorage schemaVersion 5は同じ自由座標を保存する。共通normalizeBoardDataがサーバー起動時/コマンド時/バックアップ検証時に使われ、Pages readLocalBoardも読込後の正規化データを保存する。
- Pagesのlib/local-kitchen-storage.tsとバックアップ検証のserver/restore.mjsは現在の楕円境界から座標範囲を検証する。楕円拡大後に旧端の座標を読み込んでセル中心へ移すため、旧座標検証を新しい境界判定と混同しない順序が必要。
- normalizeBoardDataはUUID形式のライブIDを配置順M-Nへ移行する。今回の幾何変更でID採番、記録、完成ボックス、温度区間を変えない。
- 旧盤面は自由配置を許したため、同じ鉄板に6個を超えるライブ楕円が保存されている可能性がある。6セルへの一対一配置はその状態を損失なく表現できない。

## 保存・移行方針

可能ならx/yのみをセル中心として使い、保存形式・schemaVersionを増やさない。行列番号は座標から導出する。新規create/moveはセル中心のみ許可し、同じ鉄板・同じセルの占有判定に統一する。モデル側でも検証し、古いクライアント/同時操作が重複セルを作らないようにする。

旧盤面で各鉄板6個以下の場合は位置を確定的にセルへ移す。各鉄板内の項目を旧座標の画面上の位置順（y、x、IDの順）で処理し、空きセルのうち旧中心に最も近いセルを割り当てる。距離は16:9描画寸法を反映した距離で比較し、同距離の場合は上段左からの行優先順で決める。これで同じ保存データは必ず同じ割当になり、正規化の再実行でもセル中心を維持する。

Undoの保存位置も移行する。UndoEntry.move.fromと旧形式のdelete UndoEntry内の楕円座標をセルへ正規化し、Undoで自由座標に戻らないようにする。移行先セルがUndo時点で占有されていた場合は既存のconflictとして状態を変更せず、別セルに勝手に復元しない。create UndoではID高水位を戻さない。

### 1鉄板に7個以上ある既存データの扱い

過去は6個を超えて配置できたため、実データで超過が起こり得る。7個以上を6セルに自動割当すると重複・楕円の上書き・削除のいずれかになり、データを損なう。ユーザー確認済みの方針として、超過時は自動移行を止め、画面に手動整理を促す。旧位置と項目は保持し、自動移動・削除・完成扱いをしない。新規配置は超過解消まで止めるが、利用者が長押しドラッグで空きのある別鉄板のセルへ移す手動整理は許可する。7個以上ある鉄板への移動や占有セルへの移動は拒否する。開始・温度調整・焼き上がり後の回収も継続できる。全鉄板が6個以下になった時点で、残っている旧自由座標を決定的にセルへ移行して保存する。Undoで超過状態に戻った場合は旧位置を含む全項目を保持し、警告を再表示する。

1鉄板あたり6個以下の場合は通常の確定的セル割り当てへ移行する。過密中に利用者が別鉄板へ明示的に移した項目だけは選択先セルを保存する。自動で隣の鉄板へ振り分けない。盤面全体の移行が止まっている間は、どちらの鉄板を移動した場合もUndo履歴に移動前の両鉄板全項目の位置を保持する。Undoは項目とタイマー/IDを変えず、移動前の盤面へ戻す。過密plateから移動した場合は元の7個以上の配置と警告状態を再現する。これには移動後も過密が残る場合（例：8枚から7枚）を含む。移行前の自由座標を復元する場合は拡大後の楕円サイズで誤拒否しない。既に保存されている旧Undo履歴（補助位置一覧なし）の復元には旧楕円サイズの衝突範囲を使う。過密中に空きセルへ移動する場合は、仮想セル割当の占有だけでなく、拡大後の楕円が旧位置の楕円と実際に重ならないことも確認する。途中版で保存された片鉄板分の補助位置一覧が入力された場合も、正規化を繰り返すたびに片鉄板の範囲を明示して保持し、両鉄板一括復元形式と誤認しない。通常状態のUndoは復元先が占有済みなら状態を変更せずconflictにする。

## 実装手順

1. セル中心・行優先index・座標変換・距離・占有判定を共有モデルに定義し、楕円1.15倍がセル境界/矢印内に収まることを確認する。
2. モデルcreate/move/undoをセル操作へ変更する。createは空きセルのみ、move/undoは対象以外に占有楕円がない場合のみ状態更新し、Undo履歴の意味を保つ。盤面全体が過密保持中の全ての移動には、移動前の両plate全項目の位置一覧を履歴へ保存し、Undoで元の配置へ戻す。セル占有は過密保持中の旧自由位置による実楕円の重なりも検証する。
3. 6個以下の旧保存位置と既存Undo復元位置を決定的に正規化する。localStorage/restoreの事前検証を調整し、PC・Pagesで読込後に正準セル中心が保存される経路を確認する。過密時は旧座標と項目を保ち、警告を表示し、新規配置と過密側セルへの移動を拒否する。別鉄板の空きセルへの明示的な移動は手動整理として許可する。
4. UIを3×2グリッドへ変更し、セルtap、drag preview、占有セル拒否、Undo後のセル開放/復帰を統合する。READMEを更新する。
5. 差分・型・各ビルドを確認し、別のLuna reviewerに依頼する。過密ケースの最終受け入れはユーザーの方針決定後に行う。

## 検証・受け入れ条件

- 各鉄板に6つの一意なセルがあり、全楕円中心がセル中心と一致し、同じセルを2項目が占めない。1.15倍の楕円と矢印がセル内に収まり、16:9のportrait/landscape/PC表示で隣セルに干渉しない。
- 空きセルtapはその中央に配置し、占有セルでは状態を変えない。dragは最近傍セルへpreviewを吸着し、空きなら移動、占有なら拒否。盤外/隙間はキャンセル。
- 新規配置Undoでセルが空き、通常のmove Undoで元セルに戻る。元セルがその後占有された場合は安全なconflictとなり状態を変更しない。盤面全体が過密保持中の移動Undoは、移動元が過密かどうかにかかわらず、移行前の全座標を復元し、項目数・ID・調理状態を維持する。過密plateからのUndoは警告状態へ戻る。Undo後もIDは再利用しない。
- 1鉄板あたり6個以下の旧位置データは、固定順/距離/tie-breakで決定的に移行し、楕円状態・記録・completionItems・採番・Undo履歴を維持する。PC/Pages再読込後も一致する。
- 7個以上の盤面は楕円を削除・自動移動・上書きせず、手動整理を促す。旧座標のまま保持し、過密側への移動と新規配置を拒否する。利用者が空きセルへ手動移動するか調理・回収で6個以下にした後、残りを決定的にセルへ移す。過密中の手動dropは旧位置に表示される楕円との実際の重なりも拒否する。
- 検証は差分レビュー、git diff --check、型確認、PC/Pagesビルド、必要ならNode構文確認、画面幅/向き別の目視確認。依頼されていないためテストは追加・実行しない。

## リスク・制約

- 最大6個/鉄板という新容量は旧自由配置から大幅な制約となる。過密状態ではグリッド外表示が一時的に残り、利用者の手動移動または調理・回収による整理が必要となる。
- greedy nearest-empty割当は決定的だが、総移動距離の最小割当とは限らない。画面上の近さを優先し、tie-breakを固定する。
- Undo履歴に残る過去座標もセル化しないと自由位置へ復元する。座標移行と履歴移行の一貫性が必要。
- モデルが占有を検証しないと、別画面・古いクライアント・同時操作経由で同じセルに複数項目が入る。UIだけの制限にしない。
- schema変更不要の見込みだが、PC起動時のSQLite正規化とPages canonical writeのタイミングを確認し、データ正規化で同期競合を増やさない。
