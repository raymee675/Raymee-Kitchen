# お好み焼きの上向き移動制限 実装計画

## 目的と期待動作

鉄板上のお好み焼きの移動を、同じ鉄板の下段から同じ列の上段へ移す操作だけに限定する。移動先は空きセルでなければならない。上段のお好み焼きでは長押しドラッグを開始できず、下段からの左右移動、同じ段への移動、別鉄板への移動もできない。無効な移動は画面上のプレビューと共通モデルの両方で拒否する。

移動が許可される対象のお好み焼きは待機中・調理中・焼き上がりのいずれでもよい。依頼に状態の限定はないため、既存の移動可能なライフサイクルを維持する。配置順ID、タイマー・温度区間、実行記録、Undo履歴の既存契約を保つ。

## 現行実装の確認結果

- 鉄板は各3列×2行の `GRID_CELLS` で表現され、行優先の `nearestGridCell` が座標をセルへ正規化する。
- `cooking-app/app/kitchen.tsx` の `down` は温度矢印以外の楕円すべてに450msの長押しタイマーを設定する。`dropTargetAt` と `up` はセルの占有と過密状態を調べるが、移動方向や移動元を制限していない。
- `cooking-app/lib/kitchen-model.ts` の `applySnapshotCommand` がmoveコマンドを共通に適用し、`gridDropBlockReason` を使って占有・過密を検査する。ここがPC版サーバーとPages版の共通強制点である。
- 移動Undoは `UndoEntry` に移動前の位置を保持し、最新の履歴から復元する。配置Undoでは連番IDの再利用条件が別途ある。今回の通常move制限をUndo復元や既存履歴の読み込みに適用してはならない。
- `kitchen.tsx` の使い方・過密警告、および `cooking-app/README.md` には、空いている任意セルや別鉄板への移動を案内する記述がある。アプリのWebMCP操作説明にも鉄板間移動という説明がある。

## 変更対象と担当

後続のGPT-6 Luna実装worker 1名が以下を担当する。workerには本計画と現行コードを渡し、他のagentも同じコードベースを編集している可能性があるため、共有変更を戻さず、差分に合わせて作業するよう伝える。担当ファイルは次のとおり。

1. `cooking-app/lib/kitchen-model.ts` — UIとモデルで再利用できる移動制約判定を追加または既存判定を拡張する。移動元IDの現在セルと移動先セルを求め、元が下段(row=1)、先が上段(row=0)、同一鉄板・同一列であることを確認した後、既存の占有・過密検査を適用する。`applySnapshotCommand` のmove分岐で必ず同じ制約を検証し、不正な直接コマンドを `KitchenError` として拒否する。外部コマンドの座標は既存契約どおり最近傍セルへ正規化する。
2. `cooking-app/app/kitchen.tsx` — 上段アイテムには長押しドラッグ用タイマーを設定しない。下段アイテムのドラッグでは共有モデルの判定を使い、許可セルだけを有効プレビューにし、左右・同段・鉄板間・占有セルを無効として示す。移動確定前にも同じ判定を通し、無効理由に合った短い案内を表示する。長押し位置のまま離した操作は従来どおり無変更として扱う。タップ・温度矢印・キーボード操作は保つ。
3. `cooking-app/app/kitchen.tsx` — 使い方、アクセシブルな鉄板説明、WebMCPのmove説明を「下段から同じ鉄板・同じ列の空いた上段へ」に合わせる。過密警告やヘルプから「別の鉄板へ移す」案内を除き、既存データの位置を維持すること、配置・移動制限があること、焼き上がり後は完成ボックスへ移して整理できることを説明する。
4. `cooking-app/README.md` — 任意セル・別鉄板へ移動できるという説明を新しい制約に更新する。過密データの案内も、今回許されない横・鉄板間移動を勧めない内容に直す。

計画ファイル `docs/oval-upward-only-movement-plan.md` は本計画作者が作成済みであり、production codeの実装担当範囲には含めない。

## 実装手順

1. セルから `column` と `row` を得る既存の `nearestGridCell` / `GRID_CELLS` を活用し、移動元IDを含む共通の移動可否判定を定義する。理由型には方向・鉄板制限と既存の占有・過密を識別できる値を含め、UIの説明に使う。
2. `applySnapshotCommand` のmove分岐で、移動元が存在することと expectedVersion 検査の後、共通判定を実行する。不許可なら状態・版数・Undo履歴を変更せず拒否する。許可時の移動は従来どおりセル中央へスナップし、ID、タイマー、温度、区間、採番値を変えず、既存のmove Undo entryを追加する。
3. UIの長押し開始を移動元の行で制御し、上段の楕円は通常のタップ・温度調整をそのまま受け付ける。下段ドラッグのプレビューとpointer-up処理は共通判定に従う。モデル側の判定を迂回する別経路を作らない。
4. moveのサーバーエラー文言、ヘルプ、過密状態の説明、SVG/アクセシブル説明、WebMCPの説明を新しい操作規則に合わせる。READMEも同じ規則を記載する。
5. 最終diffを確認し、型チェックまたはビルドと `git diff --check` で検証する。テストの追加・実行は行わない。

## 検証と受け入れ条件

- 下段セルから同じ鉄板・同じ列の空いた上段セルへのmoveだけがUIと `applySnapshotCommand` の両方で受け入れられる。
- 上段からの長押しではドラッグプレビューが開始しない。上段のお好み焼きのタップや温度矢印は従来どおり機能する。
- 下段から横、同段、別鉄板、使用中の上段へのドラッグ、および同制約に反する直接moveコマンドは副作用なしで拒否される。
- 許可moveのUndoは元の位置に戻り、既存のUndo形式・ID・タイマー・温度・記録・採番条件を変えない。既存のmove Undo履歴を復元する処理は新規移動制限により拒否されない。
- 盤面過密時に既存の配置禁止・過密鉄板へのmove拒否と、過密位置保持の挙動を維持する。警告文は移動制限と矛盾しない。
- READMEと画面内案内に任意セル移動・別鉄板移動の説明が残らない。
- テストは追加・実行せず、型チェック/buildとdiff checkの結果を報告する。

## リスクと未決事項

- 過密な旧データを別鉄板へ手動移動して整理する既存案内は新仕様と両立しない。位置は保持し、警告は焼き上がり後に完成ボックスへ移す整理方法を案内する。正規セル配置が復帰する既存条件（両鉄板とも6枚以下）は変更しない。
- 過密データでは正規セル中心にない旧座標が保持される場合がある。移動元行は既存の最近傍セル判定にそろえ、UIとモデルで異なる判定をしない。
- 通常移動の方向制約をUndo経路にも誤って適用すると、古いmove履歴が復元できなくなる。Undoは記録済み位置復元のまま制限対象外とする。
- 調理状態による移動可否は依頼で指定されていないため、新たな状態制限は設けない。
