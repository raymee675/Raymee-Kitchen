# 提供タイマーのID呼び出し実装計画

作成日：2026年10月13日　｜　状態：実装・検証完了。2026年10月14日にGitHub Pages公開を確認。対象は現在のPages運用と共有モデル・既存PC経路の整合。

## 2026年10月14日の仕様修正

ユーザーの指示により、以下の初版設計の「文字入力検索とタイマーカード表示を分ける」方式を廃止する。楕円のm・n選択と中央タップを既存の `findDeliverySearchMatches` に直結し、同じ提供状況の詳細だけを表示する。文字入力検索欄とタイマーカードは削除。中央タップは照会のみで、`recall` コマンドを送らず提供状態や保存データを変更しない。ID照合・再採番・結果内の画面ID／記録ID文言は変更せず、ID改善はユーザーへの説明・提案に留める。

型確認・Pages/PCビルド成功。UI lintはエラー0・既存警告2件。ブラウザーで中央タップの詳細表示、矢印だけでは結果を変更しないこと、該当なしの表示、文字入力欄とカードの非表示を確認。テストスイートは実行していない。

以下は初版の設計・公開履歴であり、修正後のUI仕様には本節を優先する。

## 目的と期待する動作

焼き上がった赤い楕円を回収すると、その保存時刻を起点に30分の提供期限を内部で保持する。新しく回収した完成品は最初は完成ボックスのカードに表示しない。お好み焼きに似た楕円アイコンに `m` と `n` の左右ボタンを各1組配置し、現在の画面ID `m-n` を選択して中央をタップすると、その完成品のタイマーを完成ボックスへ表示する。

- `m` は1〜8、`n` は1〜24。初期選択は `1-1` とし、上下限の矢印を無効化して範囲外へ進めない。矢印では選択だけを変更し、中央タップで初めて呼び出す。
- 呼び出しは複数追加できる。残り時間と「提供可能／提供不可」を元の期限から求め、30分を再開始しない。非表示中に期限が到達した完成品も呼び出して「提供不可」と表示する。
- 表示したカードのタップによる提供確定・期限切れ取り出しは現在の `remove` 動作を維持する。新しい非表示操作や自動非表示は追加しない。
- 非表示・呼び出しによってIDを変更しない。完成品の提供・取り出しなどでIDを詰め直す現在の全体規約は維持する。呼び出しに使うのは現在の画面IDであり、CSVの記録IDとの同時検索は行わない。
- すでに呼び出したIDは重複追加しない。未完成のID、該当完成品のないIDは理由を案内し、記録やタイマーを作らない。提供済み記録を探す既存の文字入力検索は残す。

## 現行実装の確認結果と制約

- `cooking-app/lib/kitchen-model.ts` の `collectRecord` は回収時刻と30分期限を作る。`completionStatus` / `completionTimer` は絶対期限から状態を導くため、非表示中も別の常駐タイマーなしで正しく判定できる。
- `CompletionItem` は画面ID、内部 `entityKey`、作成順、versionを保持し、記録のサービス時刻は同じ `entityKey` の `ExecutionRecord` にある。`completionItems` は表示カードだけでなく、採番・容量・Undo整合の対象である。非表示品をこの配列から取り除く設計は採用しない。
- 赤楕円の `remove` は現在、実行記録と `CompletionItem` を原子的に作り、その全配列を画面に表示する。提供 `remove` は保存処理時刻が期限より前なら提供済み、期限以上なら提供不可として確定する。期限到達だけでは項目や記録を削除しない。
- `relabelEntities` は鉄板と完成品の全体を作成順に連続採番するが、再採番だけではversion / generationを更新しない。呼び出しリクエストでは `entityKey` も照合して、送信後の再採番で別の完成品を取り出さないようにする。
- `use-kitchen-local.ts` は最新保存状態の読込、モデル操作、保存、表示更新を直列化する。ID付きコマンドのpending識別は内部keyへ解決されるため、新コマンドも現在の経路を利用できる。`use-kitchen.ts` のPC側はIDをpending識別に使う。
- Pagesの保存schemaは11。`local-kitchen-storage.ts` のJSONバックアップも同じ正規化経路を使う。PCの `server/storage.mjs` と `server/restore.mjs` も共有の `normalizeBoardData` を使い、`completionItems` の各項目をそのまま保存する。
- 既存の文字入力検索は画面IDと記録IDの両方を検索するため、呼び出し処理へ流用すると曖昧になる。検索での「提供可能」は完成品が内部配列にあり期限前なら成立させ、画面表示の有無とは分ける。
- 作業開始時点で `app/kitchen.tsx`、`app/globals.css`、`lib/kitchen-model.ts`、`lib/use-kitchen-local.ts`、構成正本に未コミット変更があり、`local-timestamp-clock.ts` も存在する。既存差分を保全し、今回の対象箇所だけ変更する。

## 状態・コマンド・保存の契約

`CompletionItem` に `isRecalled?: boolean` を追加する。正規化では欠落値を `true` として読み、旧完成ボックスに表示されていたカードをそのまま表示する。値が存在するときはbooleanだけを許可し、不正なデータを黙って補正しない。新規回収では `isRecalled:false` を保存する。

`Command` に独立した `recall` バリアントを追加する。項目は `operationId`、現在の `id`、`expectedVersion`、必須の `expectedEntityKey`、既存規約どおりの `expectedGeneration`。`parseCommand` はID、version、内部key、generationを検証する。

`applySnapshotCommand` の `recall` は完成品を現在のIDから検索し、内部key・versionを照合してから、対象の `isRecalled` だけを `true` にしversionを1増やす。非表示で期限切れの完成品も対象にできる。すでに `true` の場合は同じ項目を保ち、配列・記録を追加しない。記録の開始時刻・期限・提供時刻・不可時刻、採番、既存Undo履歴は変更しない。未完成や該当完成品なしは固有の案内を返し、再採番で内部keyが一致しない場合はconflictとして拒否する。

画面は全 `completionItems` と `isRecalled !== false` の表示用配列を分ける。採番・保存・検索・バックアップの総数は全体を用い、カード描画は表示用配列を用いる。画面上は「表示中」と「内部で保管中」の数を区別し、呼び出し前にも完成品があることを確認できるようにする。既存の完成ボックスショートカットの件数も意味を揃える。

Pages保存schemaを12へ上げる。旧schema 1〜11と旧JSONバックアップは読込可能とし、完成品の欠落フラグを `true` に補う。schema 11で導入した `strictPublicIds` / `strictArchiveIds` の適用閾値は11に固定する。schema 12の読込では新フラグの存在・boolean型を確認し、不正な新形式を旧データとして移行しない。保存とバックアップ出力では正規化後のbooleanを保存する。

PC保存JSON・復元検証は共有正規化で同じフラグを維持できるため、必要な整合がある場合にだけ変更する。既存API経路で新コマンドを通し、WebMCPのコマンド説明・enum・schemaに `recall` と `expectedEntityKey` を追加する。CSV列と記録内容は変更しない。

## 検証と受け入れ条件

テストは追加しない。型確認、lint、Pagesビルド、共有型・APIへの影響を確認するPCビルド、差分の形式確認、ブラウザーでの手動操作確認を実施する。確認は実際に行った内容だけ報告し、未実施のテストや実機確認を成功扱いにしない。

- 赤楕円を回収すると鉄板から消え、完成記録と元の30分期限が保存され、完成品のカードは表示されない。内部完成品の件数には含まれる。
- `2-5` の内部完成品を12分後に呼び出すと、残り18分と提供可能を表示する。呼び出し時刻に開始時刻・期限を更新しない。
- 呼び出し前に期限を過ぎた完成品は、呼び出すと残り0と提供不可を表示する。境界は既存どおり `now >= serveDeadlineAt`。
- 複数IDを呼び出すとカードを追加して保持し、同じIDの再呼び出しでは重複しない。矢印のみでは保存・呼び出しを行わない。
- 未完成・対象なしの呼び出しでは理由を案内し、記録とタイマーを作らない。ID再採番で対象keyが変化した古い呼び出しは拒否する。
- カードタップは期限前に提供済み、期限以降に提供不可として確定する。呼び出し操作自体では提供確定しない。
- 非表示品も採番対象であり、呼び出しの前後に画面IDを変更しない。他項目の削除・提供時の全体再採番とアーカイブ記録IDは従来どおり。
- 再読込・画面復帰・JSONバックアップ往復で、非表示／表示フラグと開始時刻・期限を保持する。旧完成品は表示を維持する。不正な新フラグは保護停止させ、既存保存を上書きしない。
- 加熱90秒、生地6個20分、長押し削除、Undo、CSVの既存差分へ無関係な変更を入れない。

## リスクと未決事項

- 画面IDは他完成品の提供等で詰め直される。利用者向け説明に現在の画面IDを使うことを記載し、新 `recall` では内部keyを照合する。全体採番方式の変更は本件に含めない。
- 呼び出し前の完成品が蓄積しても内部配列に保持するため、従来の192個上限に含まれる。自動削除や期限切れでのID解放は行わない。
- 旧データでは表示維持、新規回収では非表示になる。操作案内に切替後の動作を明示する。
- 現在の運用対象はPages。既存PC経路との型・保存互換は維持するが、ホスティング変更や公開デプロイはこの実装依頼には含めない。
- 実装を停止する未決要件はない。30分の起点、複数表示、採番規約は本計画の判断で維持する。

## 計画の自己確認

内部計測と描画を別状態にし、旧表示・新規非表示・期限判定・ID再採番の取り違え・保存往復を一つの契約で整理した。各編集ファイルの所有権と受け入れ条件を定めた。常駐タイマー、新依存、CSV変更、全体採番の改変は不要で、既存の保存・モデル経路へ局所的に追加できる。
