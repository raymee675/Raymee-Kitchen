# 待機中のお好み焼きをタップで上段へ移す実装計画

## 目的と期待動作

下段の待機中のお好み焼きについて、同じ列の上段マスが空いているときは、最初のタップで上段へ移動する。移動時にタイマーは開始しない。移動後、上段のお好み焼きをタップすると、従来どおり90秒の計測を開始する。

- 上段マスが埋まっている下段の待機中楕円は、タップで従来どおり計測を開始する。
- 上段への移動が既存の過密制約などで拒否される場合は、位置・タイマーを変えず理由を表示する。
- 調理中の下段楕円のタップ移動、焼き上がりの完成ボックス移動、温度変更、新規配置、上段からの移動禁止は維持する。
- 画面タップとEnter/Spaceは同じ操作になる。PC版・Pages版共通の画面動作とする。

## 現行実装の根拠と制約

- `cooking-app/app/kitchen.tsx` の `perform` は、待機中のタップを `start`、調理中の下段タップを上段への `move`、焼き上がりタップを完成ボックスへの `remove` に割り当てている。Enter/Spaceも同じ `perform` を通る。
- 同ファイルの `run` はmove成功を通知し、move可否の案内には `gridMoveBlockReason` と `gridMoveBlockMessage` を使う。下段からの移動先は `GRID_CELLS[source.index - GRID_COLUMNS]` で求められる。
- `cooking-app/lib/kitchen-model.ts` の共通 `applySnapshotCommand` は待機中を含むmoveを受け付け、`startedAt`、温度、区間、IDを保って座標とversionだけを更新する。上段移動・占有・過密の既存検証も適用されるため、今回の通常ケースではモデルや保存形式の変更は不要。
- PC版とPages版は共通画面・共通モデルを利用する。UIからの事前判定に加え、既存move commandの共有モデル検証を維持する。
- ヘルプ、楕円のARIAラベル、鉄板のARIA説明、フッター、WebMCP `operate_kitchen` の説明、および `cooking-app/README.md` は現在、待機中タップでタイマー開始と案内している。
- `docs/running-pancake-tap-move-plan.md` に記載された「待機中タップで開始」は今回の要求により、上段が空いている下段の待機中楕円に限って置き換わる。

## 対象ファイルと担当

1. **GPT-6 Luna実装worker（`cooking-app/app/kitchen.tsx`）**
   - `perform` の待機中tapを位置と上段セルの占有状況で分岐する。下段かつ上段が空いていれば既存のmove commandを使う。上段が埋まっていれば従来のstartを使う。
   - 先に `isGridCellOccupied` で対応する上段セルの占有を調べ、使用中ならstartする。空いている場合に `gridMoveBlockReason` で移動制約を検証し、過密など他の拒否理由は既存メッセージを表示して盤面とタイマーを変えない。move判定が過密を占有より先に返すケースでも、実際に使用中の上段セルならstart動作を保つ。
   - ARIAラベル、ヘルプ、板の説明、フッター、WebMCP説明を新しい段階的操作に合わせる。running/done/温度矢印/長押し経路は維持する。
2. **同worker（`cooking-app/README.md`）**
   - 下段待機中、上段空きの場合の「タップで移動、もう一度タップして開始」と、上段が埋まっている場合の既存開始動作を記載する。
3. **Sol coordinator**
   - 共有差分とこの計画への適合を確認する。計画はSolが所有し、実装workerは編集しない。workerは共有作業ツリーの他の変更を戻さず、割当ファイルの最新差分に合わせる。

共通モデル変更が必要だと判明した場合、workerは依存する実装を進める前にSolへ根拠を報告し、Solが対象ファイルと受け入れ条件を計画へ追記する。

## 実装手順

1. `perform`、移動先セルと占有判定、送信失敗時の案内を再確認する。
2. 下段の待機中楕円で上段が空いている場合だけ、既存のmove commandを送る。移動完了後も `startedAt === null` の待機状態を保つ。上段が占有済みなら従来のstartを送る。
3. 過密などの既存move制約を迂回せず、失敗時に理由を表示する。移動可否を確認してから適用する間の競合は既存のgeneration/version検証に任せる。
4. 移動後の上段待機楕円をタップまたはEnter/Spaceでstartできることを保ち、状態に応じたARIAラベルを用意する。
5. ヘルプ、ARIA、フッター、WebMCP説明、READMEを更新し、差分を確認する。テストは追加・実行しない。

## 受け入れ条件と検証

- 下段の待機中楕円と同じ列の上段が空いているとき、タップまたはEnter/Spaceで楕円だけが上段へ移る。計測は始まらず、開始時刻なし・温度・IDを保つ。
- 移動した上段楕円の次のタップまたはEnter/Spaceで90秒計測が始まる。
- 上段が使用中の下段待機楕円は、従来どおりタップで計測を開始する。
- 対応する上段セルが空いているのに過密制約や版数競合で移動が成立しない場合、楕円は下段に留まりタイマーも開始せず、既存のエラー経路で理由が分かる。上段セルが使用中なら、過密制約が同時にある場合も下段で計測を開始する。
- 下段の調理中楕円タップ移動、上段の調理中楕円タップ、焼き上がり移動、温度矢印、新規配置、Undoおよび記録契約に意図しない変更がない。
- README、ヘルプ、ARIA、フッター、WebMCP説明が同じ操作を案内する。
- テストは追加・実行しない。静的検証として `npm run typecheck`、`npm run build:pc`、`npm run build:pages`、ルートの `git diff --check` を行い、最終diffをレビューする。

## リスクと未解決点

- 既存モデルは過密な鉄板からの移動を拒否する。対応する上段セルが空いていても過密制約が優先される場合があるため、制約を迂回せず待機状態のまま理由を示す。対応する上段セルが実際に使用中なら、移動を試みず待機中タップの従来動作で計測を始める。
- 上段が占有済みの場合は元の動作（1回のタップでタイマー開始）を残す。利用者にはヘルプとアクセシブルな説明で、空き状況による動作の違いを明示する。
- 操作中に別端末が盤面を変更する可能性がある。既存のgeneration/version検証を維持し、拒否時に古い画面から誤った移動や開始を確定しない。
